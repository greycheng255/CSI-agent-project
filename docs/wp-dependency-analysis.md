## 2. 逐项分析

### WP-2 ← 被依赖项分析

| 被谁依赖 | 依赖内容 | 必须等 WP-2 完成吗 |
|---------|---------|-------------------|
| WP-3 | Agent 数据（标签、技能、语义搜索）用于匹配引擎 | ✅ 是 — WP-3 的 `TaskMatchingService` 需要查 `agent_capabilities`、`agent_tags`、`agent_embeddings` |
| WP-5 | MCP 读 Tool: `platform.agent.search` / `platform.agent.get` | ✅ 是 — 需要 `AgentDiscoveryService` |
| WP-6 | Agent Card Schema 校验、注册流程验证 | ⚠️ 半依赖 — 文档部分可并行，代码部分需 WP-2 表结构就绪 |

### WP-3 ← 被依赖项分析

| 被谁依赖 | 依赖内容 | 必须等 WP-3 完成吗 |
|---------|---------|-------------------|
| WP-4 | 订单由选标创建 (`selectBid → Order`) | ✅ 是 — 没有任务和报价就没有订单 |
| WP-5 | MCP 写 Tool: `platform.order.create` / `platform.quote.submit` | ✅ 是 — 需要 TasksService 和 BidsService |

### WP-4 ← 被依赖项分析

| 被谁依赖 | 依赖内容 | 必须等 WP-4 完成吗 |
|---------|---------|-------------------|
| WP-5 | MCP 写 Tool: `platform.order.update_execution` / `platform.artifact.attach` | ⚠️ 半依赖 — 接口已存在，WP-5 只是包装，可并行开发 |

### WP-5 ← 特殊性

- **读取 Tool** (5个): 几乎不受阻，只要对应 Service 在就行
- **写入 Tool** (5个): 依赖 WP-2/3/4 的 Service 方法就绪
- **文件冲突**: `app.module.ts` 是唯一冲突点（各 WP 都要注册模块）

### WP-6 ← 特殊性

- **文档部分**: 零依赖，第一天就能开始写
- **代码部分**: 依赖 WP-2 的表结构就绪后才能写 `AgentCardService` 的具体实现

## 4. 推荐执行方案

### 方案: 串行主干 + 局部并行

```
Day 1-2    Day 3-4    Day 5-6    Day 7-8    Day 9-10
   │          │          │          │          │
   ├─ WP-2 ──┤          │          │          │
   │  (4天)   │          │          │          │
   │          ├─ WP-3 ──┤          │          │
   │          │  (3天)   │          │          │
   │          │          ├─ WP-4 ──┤          │
   │          │          │  (2天)   │          │
   │          │          │          ├─ WP-5 ──┤
   │          │          │          │  (2天)   │
   │                    │          │          │
   ├────── WP-6 ────────┤          │          │
   │      (2天, 文档可   │          │          │
   │       提前启动)     │          │          │
   │                    │          │          │
```

| 阶段 | 工作 | 并行度 |
|------|------|--------|
| **第 1-2 天** | WP-2 (核心) + WP-6 (文档部分) | 🔀 并行 |
| **第 3-4 天** | WP-3 (任务+报价) | 🔂 串行 |
| **第 5-6 天** | WP-4 (订单+交付) | 🔂 串行 |
| **第 7-8 天** | WP-5 (MCP Server) | 🔂 串行 |
| **第 9-10 天** | 联调 + 端到端测试 + Bug 修复 | 🔀 全员 |

### 为什么不能大范围并行

1. **WP-2 是地基** — WP-3/4/5 都依赖 WP-2 产出的 Service 和表结构
2. **WP-3 → WP-4 是业务流水线** — 任务→报价→订单，天然串行
3. **WP-5 是包装层** — 必须在被包装的模块稳定后才能正确封装
4. **`app.module.ts` 是单点** — 所有模块都要在这里注册，多人同时改必然冲突

### 能并行的部分

| 并行组合 | 可行原因 |
|---------|---------|
| WP-2 + WP-6 文档 | WP-6 文档不依赖代码，Agent Card 规范可以提前写 |
| WP-3 + WP-5 读 Tool | WP-5 的 5 个读 Tool 可以在 WP-3 接口稳定后立即开始 |
| WP-4 + WP-5 写 Tool | WP-5 的写 Tool 依赖 WP-4 的接口，但接口签名已在 WP-4 设计文档中确定 |

## 5. SQL 迁移协调方案

为避免冲突，所有 SQL 统一管理：

```
backend/migrations/
├── 001_extend_agents.sql          ← WP-2
├── 002_create_agent_tables.sql    ← WP-2
├── 003_extend_tasks.sql           ← WP-3
├── 004_extend_bids.sql            ← WP-3
├── 005_extend_deliveries.sql      ← WP-4
└── 006_create_mcp_tables.sql      ← WP-5
```

按序号执行，后面的人不修改前面的迁移文件。

## 6. 风险总结

| 风险 | 概率 | 缓解 |
|------|------|------|
| WP-2 延期阻塞全局 | 中 | WP-6 文档可提前开工，WP-5 框架可提前搭建 |
| app.module.ts 合并冲突 | 高 | 每个 WP 结束后立即提交，下一个 WP 拉取最新 |
| WP-3 匹配引擎效果不达标 | 中 | 先用标签匹配兜底，语义搜索可后补 |
| MCP 协议联调耗时 | 中 | 先用 curl 脚本自动化测试，再对接 HiClaw |
| 表结构变更联动 | 低 | 迁移脚本统一编号，禁止修改已提交的脚本 |

---

## 7. 结论

> **推荐顺序: WP-2 → WP-3 → WP-4 → WP-5，WP-6 与 WP-2 并行**
>
> 总工时: 13 天（串行）→ 通过局部并行可压缩到 **10 天**
>
> 唯一真正可以并行的是 WP-2 和 WP-6（Agent 规范文档部分），其余必须串行。
