### 2.2 判定口径的取舍（本轮的核⼼设计）

契约 §22.3 的表述是「同一 Idempotency-Key 但 **payload 不同**」。若按字面比对整个 payload，会引入一个更严重的问题：**合法重试被误判成冲突**。重试时对端可能重新序列化 `sent_at`、省略或重排 `attachments`、增删未知字段——这些都不代表「内容变了」，但按字面比对就会返回 409，从而破坏 at-least-once 重试语义。

因此口径收敛为「**业务实质字段**」：

| 字段 | 是否参与比对 | 理由 |
|---|---|---|
| `order_id` | ✅ | 同一键落到不同订单必属误用 |
| `content.text` | ✅ | 唯一会真正丢失的业务信息 |
| `sent_at` | ❌ | 重试时可能被重新生成 |
| `attachments` | ❌ | 重试时可能重排/省略 |
| `from` | ❌ | 可选字段，重试时可能缺省 |
| 未知字段 | ❌ | 契约允许对端扩展 |

> 已用**专门用例**锁死该行为：只变 `sent_at` / `attachments` / 未知字段时必须仍返回 `duplicate=true`。

### 2.3 范围外

- `Idempotency-Key` 头：M 侧不读取，去重完全依赖 body 内 `mention_id`，见 L3。

## 五、实现要点

```ts
/**
 * §22.3：同一幂等键（mention_id）但 payload 不同 → 409 VALIDATION_IDEMPOTENCY_CONFLICT。
 * 只比对业务实质字段（order_id + content.text）；刻意不比 `sent_at` / `attachments` /
 * `from` —— 这些在合法重试时可能被对端重新序列化或省略，一并比对会把重试误判成冲突。
 */
private assertMentionPayloadMatches(
  row: EmployerMention,
  incoming: { orderId: string; text: string },
): void {
  if (
    row.orderId !== incoming.orderId ||
    readString(row.content?.text) !== incoming.text
  ) {
    throw new ContractError(
      409,
      CONTRACT_ERROR_CODE.VALIDATION_IDEMPOTENCY_CONFLICT,
      'mention_id reused with a different payload',
    );
  }
}
```

两处接线：

1. **幂等分支**（`findOne` 命中既有行后、返回 `mentionAck` 之前）；
2. **并发唯一约束冲突回读分支**（`save` 抛唯一冲突 → 回读 → 校验 → 再决定是 `duplicate=true` 还是 409）。

第 2 处容易被忽略：并发时两个请求同时通过 `findOne`（均为 null），先到者落库、后到者触发唯一冲突并回读。若只在第 1 处校验，并发场景下正文不同仍会被静默吞掉——正是本次要修的缺陷形态。

注意 `readString` 自带 `trim`，故两侧归一化口径一致；纯空格差异不会触发 409。

## 七、遗留问题与风险

| # | 问题 | 级别 | 说明与建议 |
|---|---|---|---|
| L1 | `CONFLICT_PROCESSING_IN_PROGRESS`（409）仍未实现 | 低 | M 侧不做「同幂等键在途」判定，并发由 `mention_id` 唯一约束兜底——结果是**不重复落库**，但不返回 409。实测 5 路并发同键：1×`duplicate=false` + 4×`duplicate=true`，0 个 409，耗时 110–195ms 无长在途窗口。已在对接说明标注「有意不实现」。 |
| L2 | 总契约对 `CONFLICT_*` 的**重试性自相矛盾** | 中 | §6.4 要求收到 `CONFLICT_PROCESSING_IN_PROGRESS` 后「延后重试」，但 §5.3 与 §22.3 又把 `CONFLICT_*` 标为 ❌ 不可重试。若 C 侧按后者实现，会把「延后重试」误当永久失败。已在对接说明中要求 C 侧澄清。 |
| L3 | `Idempotency-Key` 头 M 侧不读取 | 低 | 去重完全依赖 body 内 `mention_id`，语义上不影响正确性（该头与业务键同源）。 |
| L4 | 工作区另有未提交改动 | 低 | 「外部自托管 Agent 市场」功能的 4 个前端文件（`agentMarketApi.ts` / `agentMarketCatalog.ts` / `AgentMarketHub.tsx` / `NewTask.tsx`）属另一工作流，本轮未参与验证，未纳入提交。 |
| L5 | 交付期（`signed`）是否受理 mention | 中 | 沿用上一轮的严格口径未变，仍待 C 侧反馈。 |
