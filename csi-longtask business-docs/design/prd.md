## 第一章：文档概述

### 1.1 背景

CSI（碳硅交易平台）是一个 AI Agent 自主任务交付市场。平台的核心差异化在于：**交易双方不是人与人的雇佣关系，而是碳基（人类雇主）与硅基（AI Agent）之间的任务委托关系**。雇主发布任务 → 入驻平台的 AI 工作室（Workspace）竞标接单 → 中标后 AI 自主规划、执行、交付成果。

这与传统众包平台（猪八戒等）的本质区别在于：接单方不是人类，而是一个能够自主完成任务的 AI 系统。CSI 要解决的核心问题是：如何让雇主信任 AI 能够交付，以及如何让 AI 工作室的运营者（Agent Owner）能够高效、自动化地运营从接单到交付的全流程。

本 PRD 聚焦于这个闭环中的"长任务业务"版块——即任务发布后到交付验收的全流程。

### 1.2 目标

将 PoC/MVP 阶段积累的白话业务想法，升级为一份结构化、可落地的产品需求文档，作为：
- 技术架构设计的业务输入
- 研发团队实施的参照基准
- 公测版本（Beta）的功能边界定义

### 1.3 范围

**本 PRD 覆盖**：
- Agent Owner 入驻与 AI 工作室初始化
- 雇主任务发布
- 商机发现、竞标报价、雇主选标（Phase 1）
- Spec 契约生成与双方确认签订（Phase 2）
- AI 自主规划、执行、交付与验收（Phase 3）
- 异常场景处理（离线、超时、争议、干预）

**本 PRD 暂不覆盖**：
- 支付/结算体系（将在独立的"交易与结算 PRD"中定义）
- 评价/信誉体系（将在独立的"信用体系 PRD"中定义，但本 PRD 在商机匹配中提到评价作为匹配因子）
- 平台入驻审核/KYC 流程
- 移动端 App 适配
- 多语言/国际化

### 1.4 术语表

| 术语 | 英文 | 定义 |
|------|------|------|
| **雇主** | Employer | 在 CSI 平台发布任务、验收交付物的人类用户 |
| **Agent Owner** | Agent Owner / AI 工作室运营者 | 运营 AI 工作室的个人或组织，负责配置 Agent、编排工作流、对交付质量负责 |
| **Org** | Organization | 租户隔离的最小单位。每个 Agent Owner 入驻时自动分配一个 Org |
| **Workspace** | AI 工作室 | 参与竞标和交付的业务主体。属于某个 Org，有独立的类目、品牌、服务能力配置。类比：淘宝店铺 |
| **Agent** | Agent / AI 员工 | 实际执行工作的 AI 角色。绑定到一个 Agent Runtime，有独立的能力配置、Skills、指令集 |
| **Agent Runtime** | Runtime / 机器 | 承载 Agent 运行的计算资源（云端 K8s Pod）。Agent 注册到 Runtime 后处于可工作状态 |
| **商机** | Opportunity | Workspace 接收到的一条可竞标任务信息。是 CSI 任务大厅的"任务"在 Workspace 内部的投影 |
| **任务（大厅）** | Marketplace Task | 雇主在 CSI 任务大厅发布的需求。公开可见，可被多个 Workspace 发现和竞标 |
| **Project** | 项目 | 中标后创建的项目容器。追踪从 Spec 签订到最终交付的全过程。类比：Jira/TAPD 中的 Project |
| **Project Task** | 项目任务 | Project 内的具体工作任务。由 AI Agent 或 Agent Team 执行。类比：Jira Issue / Multica Issue |
| **Spec** | 需求规格契约 | 中标后雇主与 Agent Owner 达成的详细任务说明书，含目标、需求明细、边界、验收标准、交付物清单、最终报价 |
| **Orchestrator Agent** | 编排者 Agent | Workspace 级别的设置项，每个 Project 创建后由它驱动编排执行流程。类比：项目经理 |
| **流程画布** | Pipeline Canvas | Agent Owner 编排工作流的可视化工具，支持拖拽节点来定义竞标/签约/交付流程 |

## 第二章：用户角色与画像

### 2.1 雇主（Employer）

**画像**：有一个明确需求（如"帮我开发一个企业官网"、"写一份市场调研报告"），但不一定有技术背景。期望以合理价格获得高质量交付，过程省心。

**核心诉求**：
- 发布任务简单快捷
- 有足够多且靠谱的竞标者
- 清楚知道最终交付什么、什么时候拿到
- 交付质量有问题时有保障机制

**使用场景**：
- 浏览任务大厅，参考同类任务定价
- 发布任务（填写需求描述、附件、预算范围、期望交付时间、所属类目）
- 查看竞标方案，选择中标方
- 与中标方沟通澄清需求，确认 Spec 契约
- 接收交付物，验收或驳回

### 2.2 Agent Owner（AI 工作室运营者）

**画像**：拥有 AI 工程化能力，能够配置和运营 Agent。希望通过运营多个 AI 工作室来接单盈利。核心能力是"让 AI 能够稳定高质量地完成某类任务"。

**核心诉求**：
- 自动化发现商机（不想手动刷大厅）
- 自动化竞标报价（不想每个任务手动写方案）
- 中标后自动化交付（不想手动管理 AI）
- 交付过程可监控、可干预（出现问题时能介入）
- 运营多品类、多工作室并行接单

**使用场景**：
- 入驻初始化：注册 → 配置 Workspace 类目/品牌/能力 → 启动 Agent Runtime → 创建 Agent
- 编排竞标工作流：配置自动化竞标策略
- 编排签约工作流：配置 Spec 生成与需求澄清流程
- 编排交付工作流：配置 Orchestrator Agent
- 监控 Project 进展，处理异常
- 查看收益与工作室运营数据

### 2.3 平台管理员

**画像**：CSI 平台运营方，负责平台规则、类目体系、争议仲裁。

**核心诉求**：
- 管理平台类目体系
- 处理纠纷与仲裁
- 监控平台健康度（任务完成率、交付质量、响应时效）
- 审核异常行为

## 第三章：核心业务全景

### 3.1 三大阶段总览

```
雇主发布任务 ──────────────────────────────────────────────────────► 验收交付

┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│  Phase 1        │     │  Phase 2        │     │  Phase 3        │
│  竞标报价        │────►│  Spec 契约签订   │────►│  自主交付        │
│                 │     │                 │     │                 │
│  商机发现        │     │  Project 创建    │     │  Plan 生成/审批  │
│  竞标工作流      │     │  需求澄清        │     │  Task 拆分执行   │
│  雇主选标        │     │  Spec 生成/确认  │     │  质量保障循环    │
│                 │     │                 │     │  交付验收        │
└─────────────────┘     └─────────────────┘     └─────────────────┘
        │                       │                       │
  Workspace 操作         雇主 + Workspace 交互      Orchestrator 主导
                                                Owner 可监控干预
```

### 3.2 核心实体关系

```
Org (1) ────────< (N) Workspace
                        │
                        ├──< (N) Agent Runtime ──< (N) Agent
                        ├──< (N) 商机 (Opportunity)
                        │       └── 中标后 ──> (1) Project
                        │                       └──< (N) Project Task
                        │                               └── assignee: Agent
                        ├──< 类目/服务能力配置
                        └──< 竞标/签约/交付 工作流配置

Marketplace Task (1) ──< (N) 商机 (分布在不同的 Workspace)
```

### 3.3 各阶段衔接与数据传递

| 阶段切换 | 触发条件 | 传递的核心数据 |
|----------|---------|---------------|
| 雇主发布任务 → 商机投递 | 任务发布成功 + 类目匹配 | task_id, 类目, 标题, 描述, 附件, 预算, 截止时间 |
| 竞标完成 → 雇主选标 | Agent Owner 投递竞标方案 | opportunity_id, workspace_id, 报价, 竞标方案 |
| 雇主选标 → Project 创建 | 雇主确认选标 | 中标的商机数据, 原始任务数据, 关联附件 |
| Spec 签订 → 开始交付 | 雇主确认 Spec | spec_snapshot (结构化 JSON), 最终报价 |
| 交付完成 → 验收 | Agent 提交交付物 | deliverables 列表, 交付说明 |
| 验收通过 → 结束 | 雇主确认 | 验收结论 |

## 第四章：入驻与准备（Phase 0）

### 4.1 Agent Owner 入驻流程

**主流程**：

1. **注册账号**：Agent Owner 通过 CSI 平台注册页面创建账号。
2. **自动分配 Org**：注册成功后，系统自动为该账号创建 Org（组织），Org 名默认取账号用户名。Agent Owner 自动成为该 Org 的 Owner 角色。
3. **自动创建默认 Workspace**：系统在 Org 下自动初始化一个默认 Workspace，Agent Owner 自动成为该 Workspace 的所有者。
4. **引导配置**（可跳过）：
   - 填写 Workspace 名称、简介、品牌 logo
   - 选择经营类目（从平台类目树中勾选）
   - 填写服务能力描述（文本 + 标签）
   - 设置是否接收平台推送商机（默认开启）
5. **入驻完成**：Agent Owner 可进入 Workspace 开始配置 Agent。

**异常/边界处理**：
- 注册时账号已存在 → 提示登录
- 默认 Workspace 名与已有 Workspace 重名 → 自动追加序号
- 引导配置跳过 → 所有配置项保留默认值，类目默认为空（空类目时无法接收商机推送）

### 4.2 默认 Workspace 初始化

每个新 Workspace 自动初始化以下内容：

- Workspace 基本信息（名称、slug、描述为空）
- 成员列表：Agent Owner 一人，角色为 Workspace Owner
- Workspace 配置项及默认值：

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `receive_platform_push` | true | 是否接收平台推送商机 |
| `auto_discover_opportunity` | false | 是否自动扫描大厅发现商机 |
| `auto_discover_agent_id` | null | 自动发现商机时使用的 Agent |
| `auto_bid_enabled` | true | 是否自动触发竞标工作流；未配置工作流时自动短路，商机保持"待处理" |
| `orchestrator_agent_id` | null | Project 默认编排者 Agent |
| `project_compute_budget_ratio` | 0.3（30%） | Project 计算预算上限占报价比例（见 §7.12） |
| `budget_alert_threshold` | 0.8（80%） | 达到该比例发送提醒（见 §7.12） |

**Workspace 删除/关闭规则**：
- Workspace 下有**进行中的 Project**（非终态）→ **拒绝删除**，提示先完成或关闭所有 Project
- Workspace 下有**待处理或竞标分析中的商机** → **拒绝删除**，提示先处理或关闭
- Workspace 下所有 Project 和商机均处于终态 → 允许删除
- 删除后数据保留（审计追溯），标记为软删除，不物理清除

### 4.3 Agent Runtime 注册与生命周期

Agent Runtime 是承载 Agent 运行的计算资源（云端 K8s Pod）。

**托管策略**（2026-08-20 裁决，TS DR-12）：公测期仅支持**平台云端托管** Runtime——实例由平台 K8s 创建与管理，Agent Owner 无需自备云环境（本节主流程第 2 步的"自己云环境启动"为自托管形态，公测期不适用）。云端托管 Runtime 的 LLM 调用**强制走平台统一 LLM 网关**，不支持 Agent Owner 自定义 LLM provider（API key 等敏感凭证不进入平台托管环境）。后续版本按市场反馈与 roadmap 支持 Agent Owner **自托管注册** Runtime（如本地机器注册），自托管 Runtime 可配置自定义 LLM provider，模型费用由 Owner 自负，平台不计量不收费。

**主流程**：

1. Agent Owner 在 Workspace 中"添加 Runtime"，获取注册 Token 和连接配置。
2. Agent Owner 在自己云环境中启动 Runtime（Pod），使用 Token 连接 CSI 平台。
3. Runtime 启动后自动注册，绑定到对应 Workspace。
4. Runtime 定期发送心跳（间隔建议 30s），平台展示"在线"状态。
5. 心跳超时（建议 90s = 3 个心跳周期）后标记"离线"，关联 Agent 不可分配新任务。

**Runtime 生命周期状态机**：

```
注册 ──► 注册中 ──► 在线 ──► 离线 ──► 已注销
  │                  │  ▲        │
  └──► 注册失败       │  └────────┘ (心跳恢复)
                     └──► 离线 (心跳超时)
```

**【待确认】** 心跳超时后 Runtime 上正在执行的 Agent 任务怎么处理？
- A：立即标记失败，触发重试
- B：宽限期等待（如再等 5min），给 Runtime 恢复机会
- C：不标记失败，但暂停新任务分配

**心跳超时处理**：心跳超时后进入宽限期（5min），宽限期内恢复则任务继续；宽限期超时则标记当前任务失败，触发 Harness Loop 重试（L3）。

**Runtime 删除规则**：
- Runtime 上有处于"忙碌"状态的 Agent → **拒绝删除**，提示先等待 Task 完成或手动转移 Agent
- Runtime 上所有 Agent 均为"就绪"或"不可用" → 允许删除
- 删除后，该 Runtime 上所有 Agent 自动变为"不可用"

### 4.4 Agent 创建与配置

Agent 是实际执行工作的 AI 角色。一个 Agent 绑定一个 Runtime，一个 Runtime 可承载多个 Agent。

**创建流程**：

1. 在 Workspace Agent 管理页面点击"创建 Agent"
2. 填写基本信息：名称（必填）、简介、头像
3. 选择所属 Runtime（必选，Runtime 必须在线）
4. 选择 LLM 模型（从平台统一 LLM 网关按当前订阅套餐下发的可用模型目录中选择；云端托管 Runtime 不支持自定义 LLM provider，见 §4.3 托管策略与 §4.6）
5. 配置规则指令（System Prompt / CLAUDE.md）
6. 配置 Skills（从平台 Skills 市场选择或自定义）
7. 配置可用工具集
8. 保存完成

**Agent 状态**：

- **就绪**：配置完成，Runtime 在线，可接收任务
- **忙碌**：正在执行某 Project Task
- **不可用**：Runtime 离线或 Agent 被手动停用

**Agent 删除规则**：
- Agent 处于"忙碌"状态（有待执行或执行中的 Project Task）→ **拒绝删除**，提示先等待 Task 完成或重新分配 Task 给其他 Agent
- Agent 处于"就绪"或"不可用"状态 → 允许删除
- Agent 被删除后，该 Agent 的历史执行记录和关联 Comment 保留（审计追溯）

### 4.6 订阅套餐与 LLM 额度（2026-08-20 裁决新增，TS DR-12）

**升降级口径**：升级即时生效（按剩余周期折算差价）；降级下个计费周期生效。

**权益校验点**（Console 四处强制校验，超限/越目录即业务态拒绝并提示升级路径）：创建云端 RuntimeInstance 时校验实例数上限；选择 RuntimeProfile/Version 时校验规格目录；创建 Agent 选择模型时校验模型目录；任务派发前校验额度余额。

## 第五章：竞标报价（Phase 1）

### 5.1 商机发现：三种模式详解

商机（Opportunity）是 Marketplace Task 在 Workspace 内部的投影。一个 Marketplace Task 可以对应多个 Workspace 中的商机，但每个 Workspace 对该任务**最多只有一条商机记录**（幂等）。

#### 模式一：平台推送（Push）

**触发时机**：雇主发布任务后，由 CSI 平台异步触发匹配。

**流程**：
1. 雇主发布任务，指定类目
2. 平台匹配引擎启动，查询所有满足条件的 Workspace：
   - 经营类目与任务类目有交集
   - `receive_platform_push = true`
   - 未处于平台处罚/冻结状态
3. 对候选 Workspace 计算匹配度分数，因子包括：
   - 类目重合度
   - 服务能力标签与任务标签的语义匹配度
   - Workspace 历史完成率、雇主评分
4. 对匹配度**超过阈值**（默认 60 分，平台管理员可在后台调整）的 Workspace，生成商机记录并投递到该 Workspace 的商机 Inbox
5. 生成的 Opportunity 自动写入 `source = "platform_push"`，用于后续雇主侧的"平台推荐"标识（见 §5.6.2）

**匹配度分数仅用于投递决策**，不在雇主侧展示（避免"排名"带来的公平性暗示）。

**新 Workspace 冷启动保护**：新入驻 Workspace 无历史完成率和评分数据，匹配度可能偏低。新 Workspace 入驻后 **30 天内**享有匹配度保底——若计算分数低于阈值，自动按阈值通过（确保新 Workspace 能收到商机）。30 天后恢复正常评分。

#### 模式二：Workspace 主动拉取（Pull）

**触发时机**：由 Workspace 配置的自动拉取定时触发（如每 5 分钟扫描一次），或 Agent Owner 手动触发单次扫描。

**前提条件**：
- Workspace 设置 `auto_discover_opportunity = true`
- 已配置 `auto_discover_agent_id`（负责分析商机的 Agent）
- 该 Agent 处于"就绪"或"忙碌"状态均可（忙碌时排队等待）

**流程**：
1. 定时任务触发，检索任务大厅匹配类目的新任务列表
2. 将任务列表交给 `auto_discover_agent_id` 指定的 Agent 逐个分析：
   - Agent 阅读任务标题、描述、附件
   - Agent 评估"此任务是否在本 Workspace 服务能力范围内、是否值得竞标"
   - Agent 输出结论：匹配 / 不匹配（含判断理由）
3. 对于 Agent 判定"匹配"的任务 → 检查幂等，无重复则创建商机投递到 Inbox
4. 对于"不匹配"的任务 → 记录审计日志，不做任何处理

#### 模式三：Agent Owner 手动派发（Manual Assign）

**触发时机**：Agent Owner 在任务大厅浏览时手动操作。

**流程**：
1. Agent Owner 在任务大厅浏览任务
2. 对感兴趣的任务，点击"派发到我的 Workspace"
3. 选择目标 Workspace（若名下有多 Workspace）
4. 系统检查幂等 → 无重复则创建商机投递到 Inbox；已存在则提示"该商机已在 Workspace 中"

### 5.2 商机幂等投递机制

**幂等键**：`(workspace_id, marketplace_task_id)` —— 数据库层 `UNIQUE` 约束天然保证。

**去重逻辑**：任何模式投递前先查询该幂等键是否已有商机记录。已存在则静默跳过，不存在则创建。

**三种模式并发竞态**：数据库唯一约束保证只有一条写入成功。先写入的生效，后写入的捕获唯一冲突后静默跳过。

### 5.3 竞标席位机制

雇主发布 Marketplace Task 时可设置**竞标席位数**（即该任务最多允许多少个 Workspace 提交竞标方案）。

**规则**：
- CSI 平台设定全局最大席位数（如 20），雇主发布任务时设置的席位数不能超过此上限
- 竞标席位按 **竞标轮次（bid_round）** 计算；每一轮的席位占用独立统计
- 每个 Workspace 在**当前轮次**成功提交竞标方案后占 **1 个席位**
- 席位未满 → 符合条件的 Workspace 可继续提交竞标
- 席位已满 → 新的竞标无法提交，Workspace 侧看到的商机标注"席位已满"
- 雇主在席位未满时可以随时选标进入下一阶段，也可以等待席位填满再选
- 雇主可以随时**全部驳回**当前竞标 → 清空所有已占席位，当前已竞标的商机变为"已驳回"（终态），该任务重新开放竞标

**席位满后雇主决策倒计时（防死锁机制）**：
- 竞标席位一旦达到 `seat_limit`（席位满），触发 **72 小时雇主决策倒计时**
- 倒计时期间：席位锁定，不再接受新竞标；雇主必须在窗口内完成"选标"或"全部驳回"操作
- 触发时立即向雇主发送**紧急级通知**（站内 + 邮件 + 短信，见 §7.9）
- 倒计时期间催办节奏：第 24h 提醒级催办；第 48h 紧急级催办；第 72h 到期
- 72 小时到期仍未操作 → **系统自动执行"全部驳回"**：
  - 当前轮次所有"已竞标"商机 → "已驳回"（终态）
  - `Marketplace Task` 保持"招标中"；`bid_round += 1`；席位归档清零
  - 平台记录雇主该次超时行为，用于信誉体系评估
  - 该任务重新开放竞标（遵循 §5.6.6 再次竞标资格规则）

**任务重开竞标时的席位处理**：
- 若因"全部驳回"或"中标后 Spec 超时未确认"导致任务重新开放竞标，则视为进入**下一轮竞标**
- 上一轮所有席位占用记录归档为历史，不再占用当前轮次席位
- 新一轮席位占用数从 **0 / seat_limit** 重新开始计算
- 具备再次竞标资格的 Workspace（如 `中标失效`、`不予竞标`）在新一轮重新提交竞标方案后，**重新占用 1 个席位**

**【设计理由】** 席位机制有两个作用：(1) 防止雇主被海量竞标淹没，控制决策成本；(2) 倒逼 Agent Owner 提升竞标质量——席位有限，凑数的竞标方案等于浪费席位。

### 5.4 商机（Opportunity）状态机

**业务原则**：对同一 `Marketplace Task × Workspace`，平台始终只保留**一条** Opportunity 记录（幂等唯一）。  
这条 Opportunity 是该任务在该 Workspace 内的**唯一业务投影**，可以承载**多轮竞标历史**；重新开标时复用原 Opportunity，不创建第二条记录。

```
                        平台推送 / 主动拉取 / 手动派发
                                    │
                                    ▼
                             ┌─────────────┐
                             │   待处理     │ ◄── 初始状态
                             └──────┬──────┘
                                    │
          ┌────────────┬────────────┼────────────┐
          │ 自动触发    │ 手动触发    │ 批量触发    │
          │ (默认开启)   │            │            │
          ▼             ▼            ▼            │
   ┌──────────┐  ┌──────────┐  ┌──────────┐      │
   │ 竞标分析中│  │ 竞标分析中│  │ 竞标分析中│      │
   └────┬─────┘  └────┬─────┘  └────┬─────┘      │
        │              │              │            │
        └──────────────┼──────────────┘            │
                       ▼                           │
              ┌─────────────────┐                  │
              │ 竞标工作流执行中  │                  │
              └────────┬────────┘                  │
                       │                           │
        ┌──────────────┼──────────────┐            │
        ▼              ▼              ▼            │
  ┌──────────┐  ┌──────────────┐  ┌──────────┐   │
  │  已竞标   │  │  不予竞标     │  │  已过期   │   │
  └────┬─────┘  └──────┬───────┘  └──────────┘   │
       │                                          │
       │ 雇主操作                                  │
       │                                          │
  ┌────┼────────┐                                 │
  ▼    ▼        ▼                                 │
┌────┐┌──────┐┌──────┐                            │
│中标││未中标││已驳回│  ◄── 雇主"全部驳回"时       │
└─┬──┘└──────┘└──────┘     所有已竞标→已驳回       │
  │                                                  │
  │ Spec 超时未确认                                   │
  ▼                                                  │
┌──────────┐                                         │
│ 中标失效  │ ── 任务重开 + Owner 手动发起新一轮 ───────┘
└──────────┘
```

**状态说明**：

| 状态 | 含义 | 进入条件 | 对当前轮次是否终态 | 任务重开后是否可再次竞标 |
|------|------|---------|:------------------:|:------------------------:|
| 待处理 | 商机已投递，等待触发竞标分析 | 商机创建时自动进入 | — | — |
| 竞标分析中 | 竞标工作流正在执行 | 自动/手动/批量触发 | — | — |
| 已竞标 | 已完成竞标，方案已提交到任务大厅 | 工作流执行完毕且 Agent 决策"竞标" | — | — |
| 不予竞标 | 已分析但决定本轮不参与 | 工作流执行完毕且 Agent 决策"不竞标" | ✅ | ✅（仅任务进入新一轮时，由 Owner 手动发起） |
| 已过期 | 关联 Marketplace Task 自然过期/关闭 | 任务过期时批量更新 | ✅ | ❌ |
| 中标 | 雇主选择了该竞标方案，进入签约锁定阶段 | 雇主选标操作 | — | — |
| 中标失效 | 已中标但因 Spec 超时未确认导致签约失败 | 关联 Project 因 Spec 超时被取消 | ✅ | ✅（在原 Opportunity 上发起新一轮） |
| 未中标 | 雇主选择了其他方案 | 其他商机被选标时同任务的其他商机自动进入 | ✅ | ❌ |
| 已驳回 | 雇主执行"全部驳回" | 雇主驳回操作 | ✅ | ❌ |

**状态转移规则**：
- "待处理" → "竞标分析中"：三种触发方式均可
- "竞标分析中" → "已竞标" 或 "不予竞标"：工作流完成时自动更新
- "已竞标" → "中标"：雇主选标操作；"已竞标" → "未中标"：雇主选了其他竞标；"已竞标" → "已驳回"：雇主全部驳回
- "中标" → "中标失效"：雇主超时未确认 Spec，关联 Project 自动取消
- "中标失效" → "竞标分析中"：任务重新开放竞标后，Agent Owner 在**原 Opportunity** 上手动发起新一轮竞标
- "不予竞标" → "竞标分析中"：仅当任务进入新一轮公开竞标，且 Agent Owner 手动重新发起时允许
- "未中标""已驳回""已过期"：为 Opportunity 记录级终态，不可再次竞标

### 5.5 竞标报价工作流编排

Agent Owner 通过编排工作流来定义"商机到达后如何自动分析并决策是否竞标"。

#### 5.5.1 设计动机：为什么用流程编排？

在评估此方案之前，需要先回答一个更根本的问题：**用流程编排来解决竞标自动化，是不是正确的思路？**

**CSI 的核心挑战**：Agent 的行为是非确定性的。同一个商机给同一个 Agent，两次执行可能给出不同的分析和报价。这意味着：
- 不能靠"写死规则"（if 预算 > X then 报价 = Y）——每个任务都需要 Agent 实际阅读理解
- 不能靠"单个 prompt"——竞价决策需要多维度分析（技术可行性、成本估算、竞争策略），单次 LLM 调用不可靠

**流程编排的合理性**：
1. **多 Agent 协作是客观需要**：复杂任务的分析靠一个 Agent 不够，就像公司的销售有时候需要找技术专家评估一样。编排让 Agent Owner 能配置"先初步分析 → 复杂则路由到专家 Agent → 报价超阈值则等待 Human 审批"这种多角色协作。
2. **差异化竞争策略**：不同的 Workspace 竞标策略不同——有的激进（薄利多销）、有的保守（只接高把握任务）。编排不是写死规则，而是让 Agent Owner 把策略**显式化**。若没有编排，每个 Workspace 的竞标行为趋同（都用同一个 Agent 直接出价），CSI 的"差异化竞标"价值就丧失了。
3. **Human-in-the-loop 的自然承载**：Agent Owner 需要在某些关键节点介入（如报价金额超预期），编排的"暂停-审批-继续"模型天然匹配此需求。

**反方观点与边界**：
- ❌ "编排过于复杂，Agent Owner 不会用" → 提供预设模板，0 配置即可运行；进阶用户才深入自定义
- ❌ "自由拖拽画布开发量大" → 公测版可先用开源方案（HiveWard/Clutch 的编排引擎均可参考），且这是 Agent 主导开发的——我们自己的 AI 来写编排引擎的代码
- ⚠️ **真正的风险不在编排工具本身，而在 Agent 执行的不确定性**：再怎么编排，Agent 节点的输出仍然是非确定性的。因此必须在编排中引入**校验节点**（检查 Agent 输出的报价是否在合理范围、竞标方案是否包含必需字段），以及 **Harness Loop**（Agent 输出不合格时自动重试）

**结论**：流程编排是正确方向。Phase 1（竞标）和 Phase 2（Spec 签订）适合用**预配置工作流**（Agent Owner 设计一次，每次商机到达时自动执行），Phase 3（交付）适合用 **Agent 动态生成 Plan + Owner 审批**（每个 Project 都不同）。详见下文各章节。

#### 5.5.2 工作流节点类型

**目标交付方式**：公测版优先做可视化拖拽画布（选项 C）。若开发周期确实不允许，则用表单式配置（选项 B）作为兜底，确保功能完整性不因 UI 形态而妥协。

| 节点类型 | 功能 | 典型用途 |
|----------|------|---------|
| **开始节点** | 载入上下文（商机数据、雇主任务详情、Workspace 能力描述） | 每个工作流的入口 |
| **Agent 节点** | 将上下文交给指定 Agent 执行分析，输出结构化结果 | 竞标分析、方案撰写、报价计算 |
| **Agent Team 节点** | 上下文交给一个 Agent Team 协作处理 | 复杂任务的多 AI 协同分析 |
| **条件判断节点** | 基于上游节点输出做分支决策 | 决定是否竞标、路由到不同处理路径 |
| **工具节点** | 调用平台 API（更新状态、提交方案、发送通知） | 提交竞标方案至任务大厅 |
| **路由节点** | 基于条件将流程导向不同目标节点 | 简单/中等/复杂任务走不同路径 |
| **Human 审批节点** | 暂停流程，等待 Agent Owner 审批 | 报价金额超阈值时需人工确认 |
| **结束节点** | 推进商机状态并结束流程 | 标记处理完成 |

#### 5.5.3 工作流触发规则

**核心规则**：
- Workspace 有一个开关 `auto_bid_enabled`（**默认开启**），控制是否自动触发竞标工作流
- 开关开启 + 已配置竞标工作流 → 新商机投递时**自动触发**工作流，商机状态：待处理 → 竞标分析中
- 开关开启 + **未**配置竞标工作流 → **静默短路**，商机停留在"待处理"，Agent Owner 需手动触发或先配置工作流
- 开关关闭 → 所有新商机停留在"待处理"，需手动触发

**手动触发**："待处理"状态的商机卡片上有"竞标"按钮，Agent Owner 点击后手动触发。

**批量触发**：在商机管理页面，Agent Owner 可多选"待处理"的商机，一键批量触发竞标。

### 5.6 竞标结果与雇主选标

#### 5.6.1 竞标方案投递

商机工作流执行"提交方案"后：
- 竞标方案（文本 + 报价金额 + 预计交付时间 + Workspace 品牌信息）**同时写入两个位置**：
  - Workspace 侧：商机记录的 `bid_content` 字段
  - 雇主侧：Marketplace Task 的竞标列表（占据 1 个竞标席位）
- 商机状态 → "已竞标"

**雇主在任务详情页看到**：Workspace 名称/品牌、报价金额、预计交付时间、竞标方案摘要、竞标时间、**"平台推荐"标签**（当且仅当竞标来源为平台推送时展示，见下方规则）。

**"平台推荐"标签（Platform Recommended Label）**：

**触发规则**：竞标记录对应的 Opportunity `source = "platform_push"` 时，该竞标在雇主侧竞标列表中额外显示"平台推荐"标签。

**展示位置**：
- 雇主侧竞标列表卡片右上角，与 Workspace 名称同排
- 竞标详情页顶部横幅
- 标签样式：绿色徽章（避免与"新店"红色标识冲突），文案统一为 **"平台推荐"**，鼠标悬停显示 Tooltip："该 Workspace 由 CSI 平台基于类目匹配和运营质量主动推送邀请参与竞标"

**展示前提（避免误导）**：
- 仅在竞标当轮次（`bid_round`）内 Opportunity 来源为 `platform_push` 时展示
- 若 Workspace 在下一轮中标（原来源为 `pull` 或 `manual_assign`）→ **不展示**该标签
- 平台可对**处于处罚/冻结**状态的 Workspace **临时下架**"平台推荐"标签（即使 `source = "platform_push"` 亦不展示），以避免品牌背书风险

**业务效果（双向激励）**：
- **对雇主**：明确"这是平台基于运营数据主动匹配的 Workspace"，引起注意与信任，提高选标质量
- **对 Agent Owner**：被平台推送 = 被平台"背书"，运营好的 Workspace 更容易在竞标中脱颖而出；直接激励 Agent Owner 持续维护 Workspace 的完成率、评分、服务承诺，形成正循环
- **对平台**：将"推荐权"作为运营抓手——高质量 Workspace 获得更多曝光，形成生态自净

**注意事项**：
- "平台推荐"仅代表推送来源，**不代表平台对竞标方案的质量背书**（详情页 Tooltip 需明确此边界，保护平台责任边界）
- 标签展示与综合分排序**互不干扰**（综合分不因 `source` 加权）；标签只是视觉信号

**竞标列表默认排序（综合分排序）**：

雇主侧竞标列表默认按 **综合分** 从高到低排序，综合分公式为：

```
综合分 = 0.4 × 历史评分归一化 + 0.3 × 报价性价比 + 0.3 × 提交时间新鲜度
```

- **历史评分归一化**：Workspace 的历史平均评分（0-5 星）线性归一到 [0, 1]；新 Workspace（历史任务 < 3 单）取行业平均分作为初始值
- **报价性价比**：`(预算中位数 - 该报价) / 预算中位数`，越低分越高；但报价**低于同轮次预算中位数 50%** 时反向扣分（防止恶意低价倾销）
- **提交时间新鲜度**：距当前时间越近分数越高，24 小时内提交的方案得满分，超过 72 小时开始衰减

**排序规则细则**：
- 综合分**仅用于默认排序**，**不在雇主侧展示分数值**（避免公平性质疑）
- 雇主可手动切换排序维度：报价从低到高 / 报价从高到低 / 提交时间倒序 / 评分从高到低
- 综合分数值在平台后台可查（供运营调优权重）

**【设计理由】** 避免"先到先得"导致 Agent Owner 疯狂拼手速；综合分平衡质量（评分权重最高）、价格（防低价倾销）、时效三要素。

#### 5.6.2 雇主选标

**操作**：雇主在竞标列表中选择一个方案，点击"选择此方案"。

**选标后系统行为**：
1. 选中商机 → "中标"
2. 同任务下所有其他"已竞标"商机 → "未中标"
3. 通知中标 Workspace（Inbox 中标消息）
4. 通知未中标 Workspace（Inbox 通知）
5. Marketplace Task 状态 → "已选标"
6. **自动触发 Project 创建**（见第六章）

#### 5.6.3 雇主全部驳回

**操作**：雇主在竞标列表页点击"全部驳回"。

**驳回后系统行为**：
1. 当前所有"已竞标"商机 → "已驳回"（终态，等同于"未中标"，雇主不认可这些方案）
2. 竞标席位全部清空，任务重新开放竞标
3. **之前未竞标过的** Workspace 可以继续向此任务提交竞标
4. 已被驳回的 Workspace **不可再次竞标同一个任务**——雇主已经否决过，不允许重复提交

#### 5.6.4 Marketplace Task 过期

**规则**：
- CSI 平台设定全局任务最大有效期（如 30 天），雇主发布时可设置更短的有效期
- 任务发布后，无论竞标席位是否已满、是否有 Workspace 提交竞标，超过有效期后雇主仍未选标 → `Marketplace Task` 状态 → **已过期**（对应附录 D.1）
- 任务进入"已过期"时，所有关联的"已竞标""待处理""竞标分析中"商机 → 批量更新为"已过期"（终态）

#### 5.6.5 雇主选标后不可反悔

**【已确认】** 公测版本选标后立即锁定，不可反悔。Spec 签订前的反悔机制留待后续版本基于用户反馈再考虑。

#### 5.6.6 任务重新开放竞标与再次竞标资格

**触发场景**：
- 雇主执行"全部驳回"，任务重新开放竞标
- 已中标 Project 因 Spec 超时未确认而取消，任务重新开放竞标

**核心规则**：
- 平台不会为同一 `Marketplace Task × Workspace` 创建第二条 Opportunity；所有后续轮次均复用原 Opportunity 记录
- 每次任务重新开放竞标时，`Marketplace Task` 进入下一 `bid_round`；上一轮席位全部归档清零，新一轮重新计算席位占用
- 重新开放竞标时，能否再次竞标取决于该 Workspace 当前 Opportunity 状态：

| 当前 Opportunity 状态 | 是否可再次竞标 | 方式 |
|---|---|---|
| 中标失效 | ✅ | 在原 Opportunity 上由 Agent Owner 手动发起新一轮竞标 |
| 不予竞标 | ✅ | 仅限任务进入新一轮公开竞标后，由 Agent Owner 手动发起 |
| 未中标 | ❌ | 视为已消耗竞标机会，不可再次竞标 |
| 已驳回 | ❌ | 雇主已明确否定，不可再次竞标 |
| 已过期 | ❌ | 原任务已自然失效 |

**设计原则**：竞标机会是稀缺资源。Workspace 一旦正式参与竞标并被雇主否决（未中标/已驳回），即视为该任务上的竞标机会已消耗；只有"签约失败"（中标失效）或"上一轮主动放弃"（不予竞标）的 Workspace，才可在任务进入新一轮时重新判断是否参与。

#### 5.6.7 Workspace 展示页（雇主信任建设）

**背景**：传统众包平台雇主可以看到接单方的真人简历、案例作品、客户评价。CSI 的 Workspace 是"AI 工作室"，雇主需要一个可信的载体来了解每个 Workspace 的能力和信誉。

**触发**：雇主在竞标列表中点击 Workspace 名称/品牌 → 进入 Workspace 展示页（详情页）。

**展示页必备内容**：

| 模块 | 数据来源 | 说明 |
|------|---------|------|
| **能力标签** | Agent Owner 自填 | 最多 5 个标签，如"电商文案 / SaaS 官网 / 数据分析报告" |
| **服务承诺** | Agent Owner 结构化选择 | 响应时长（如 24h / 48h）、修订次数保证、退款政策 |
| **历史交付案例** | Agent Owner 上传 | 最多 6 个案例（含标题、简介、脱敏截图/摘要），支持"公开 / 仅评审可见"两种权限 |
| **信用数据（脱敏）** | 平台自动生成 | 完成任务数、平均评分（星级）、按时交付率、纠纷率 |
| **首页公告** | Agent Owner 自定义 | 200 字以内文本，用于展示品牌主张或近期活动 |
| **新店标识** | 平台自动 | 历史任务 < 3 单的 Workspace 显示"新店"标识（对齐 §5.1 冷启动保底） |

**权限与合规**：
- 案例上传需 Agent Owner 声明"已获客户授权公开"或"已充分脱敏"，平台保留下架权
- 信用数据（评分、纠纷率）由平台自动计算生成，Agent Owner 不可修改
- 展示页在 Phase 1 竞标阶段对雇主可见；未参与竞标的第三方无法访问（避免品牌被恶意爬取）

**Phase 1 必做**：Workspace 展示页是 CSI 冷启动阶段"雇主信任"的核心载体，公测版本必须交付；Agent Owner 侧同时需要一个"店铺门面"来沉淀品牌资产。

#### 5.6.8 竞标方案差异化提示

**背景**：如果所有 Workspace 使用类似的 Agent 模型和竞标工作流模板，容易导致提交的竞标方案高度同质化，让雇主难以做出有效决策，稀释 CSI"差异化竞标"的价值。

**规则**：
- Workspace 提交竞标方案时，平台自动计算该方案与**该 Marketplace Task 下已提交竞标方案**的**语义向量相似度**
- 相似度 ≥ **85%** → 提交界面展示**软警告**，不阻断提交：

```
⚠ 您的竞标方案与已有 N 个方案相似度较高（xx%）。
  高度同质化的方案容易被雇主忽略，建议差异化后再提交。
  您仍可以选择：
  [继续提交]  [返回修改]  [触发工作流重新生成]
```

- 相似度 < 85% → 无提示，正常提交
- 相似度数据不对雇主展示；平台内部保留用于监控"工作流模板套壳"等异常竞争行为

**【设计理由】** 不强制干预 Agent Owner 的自主决策（相似度算法可能存在误差），但传递"同质化竞争无效"的信号；同时为平台后续治理提供数据基础。

## 第六章：Spec 契约签订（Phase 2）

### 6.1 概述

雇主选标后，中标 Workspace 与雇主之间进入**需求澄清与契约签订**阶段。这个阶段的产出物是一份双方确认的 **Spec 契约**——它把雇主原始的任务描述（可能模糊、不完整）转化为一份结构化的、可验收的、双方认可的详细任务规格书。

**Spec 契约的核心价值**：
- 防止需求理解偏差导致的交付纠纷
- 为 Phase 3 的交付验收提供客观依据
- 锁定最终报价（中标时的报价是初步报价，Spec 签订后锁定为最终报价）

### 6.2 Project 创建

雇主选标后，系统**自动**在中标 Workspace 下创建 Project。

**Project 创建时自动带入**：
- 雇主原始任务数据（标题、描述、类目、预算、期望交付时间）
- 雇主上传的附件（需求文档、参考图等）→ 自动挂载为 Project 附件
- 中标商机的竞标方案（作为 Spec 生成的参考上下文）
- 报价信息

**Project 初始状态**：**"契约签订中"**

**Marketplace Task 与 Project 的关系**：一个 Marketplace Task 在同一时刻最多有一个**活跃的** Project（非终态）。但如果雇主的选标 → Spec 超时取消 → 重新选标循环了多次，历史上可以有多个已终态（已取消/已完成）的 Project 关联同一个 Marketplace Task。即：**一对一活跃，一对多历史**。

### 6.3 Spec 生成工作流编排

与竞标报价阶段类似，Spec 生成与签订也可以通过**编排工作流**来自动化。Agent Owner 在 Workspace 中预设 Spec 签约流程，每个 Project 创建后自动触发执行。

#### 6.3.1 Spec 签约工作流节点类型（在竞标工作流基础上新增）

| 节点类型 | 功能 | 典型用途 |
|----------|------|---------|
| **发起对话节点** | Agent 主动发起与雇主的澄清对话，在 Project 的对话区创建讨论线程 | 需求不清晰时向雇主提问 |
| **等待雇主回复节点** | 暂停流程，等待雇主回复后再继续 | 雇主澄清问题的标准等待 |
| **提交 Spec 节点** | 将生成的 Spec 推送到雇主侧，请求雇主查阅确认 | Spec 提交 |

#### 6.3.2 示例工作流

```

       ▼
[Agent: 需求分析Agent] ── 深度阅读雇主原始任务，识别模糊点、矛盾点、缺失点

       ▼

       │
  ┌────┴────┐
  ▼         ▼
[清晰]    [不够清晰]
  │         │
  │         ▼
  │    [发起对话节点: Agent 生成澄清问题列表，创建讨论线程]
  │         │
  │         ▼
  │    [等待雇主回复节点]
  │         │
  │         ▼
  │    [Agent: 分析雇主回复，判断疑问是否已全部澄清?]
  │         │
  │    ┌────┴────┐
  │    ▼         ▼
  │  [已澄清]  [仍有疑问]
  │    │         │
  │    │         └──► 回到 [发起对话节点]（循环，最多 N 轮）
  │    │
  │    ▼

       │

       │

  ▼         ▼
[确认]    [不认可]

  │    [Agent: 分析雇主不认可原因，修订 Spec]
  │         │

#### 6.3.3 需求澄清循环的边界控制

**【设计要点】** 白话文稿中说"直到雇主认可契约签订为止"——这在业务上是对的，但工程上必须有循环次数上限，否则可能导致无限循环消耗 Agent Owner 的计算资源。

**两阶段循环独立计数原则**：
- **需求澄清阶段**（Spec 生成前，Agent ↔ 雇主的对话式澄清）：最多 **5 轮**
- **Spec 驳回修订阶段**（Spec 生成后，雇主驳回 → Agent 修订）：最多 **3 轮**
- 两阶段**独立计数、不共享额度**——需求澄清用完 5 轮后，Spec 修订额度仍是完整的 3 轮

**需求澄清轮次上限**：
- 默认最多 **5 轮**（Agent 提问 → 雇主回复 → Agent 再分析，算 1 轮）
- 达到上限后：Project 进入 **协商取消中** 状态，双方可选择：
  - (a) Agent Owner 主动放弃（无违约金，不计入违约率）
  - (b) 雇主主动取消（无违约金，不计入违约率）
  - (c) 升级人工客服介入协助澄清
- 平台不强制关闭，但停止自动循环消耗资源

**Spec 驳回修订上限**：
- 默认最多 **3 轮**（雇主驳回 → Agent 修订 → 重新提交，算 1 轮）
- 达到上限后：处理规则同上（进入协商取消中，三选一）

**【设计理由】** 超限触发的取消**不计入 Workspace 违约率**，避免双方在 Phase 2 因担心违约而硬着头皮进入执行阶段引发更大纠纷；鼓励双方在需求探索/契约打磨阶段及时止损。

### 6.4 Spec 结构定义

**【设计要点】** 白话文稿中对 Spec 的描述是"描述了任务目标、需求明细条目、任务边界、验收标准、交付物清单、最终报价等等"。Spec 不能只是一段 Markdown 文本——它必须是**结构化数据**，因为：
- Phase 3 的交付验收需要逐条匹配验收标准（文本无法自动化校验）
- 雇主确认后 Spec 需要锁定为不可篡改的快照
- 后续若需变更 Spec，结构化数据才能做 diff 对比

**Spec 必需字段**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `spec_id` | string | Spec 唯一标识 |
| `project_id` | string | 所属 Project |
| `version` | int | 版本号（从 1 开始，每次修订递增） |
| `goal` | string (text) | 任务目标概述（一句话） |
| `requirements` | array of Requirement | 需求明细条目列表 |
| `scope_boundary` | string (text) | 任务边界说明（明确哪些**不在**交付范围） |
| `acceptance_criteria` | array of AcceptanceCriterion | 验收标准列表 |
| `deliverables` | array of Deliverable | 交付物清单 |
| `final_price` | number | 最终报价（锁定后不可变更，除非双方协商改 Spec） |
| `estimated_delivery_date` | date | 预计交付日期 |
| `revision_limit` | int | 允许的交付修订次数（默认 2 次） |
| `employer_confirmed_at` | datetime | 雇主确认时间 |
| `snapshot_hash` | string | Spec 内容哈希（用于防篡改校验） |

**子结构定义**：

```
Requirement {
  id: string
  title: string           // 需求标题，如"用户登录功能"
  description: string     // 详细描述
  priority: "must" | "should" | "nice_to_have"
}

AcceptanceCriterion {
  id: string
  requirement_id: string  // 关联的需求条目
  description: string     // 可验证的验收条件，如"输入正确账号密码后可成功登录"
  verification_method: "manual" | "automated"  // 验收方式
}

Deliverable {
  id: string
  name: string            // 交付物名称，如"用户登录模块源代码"
  type: "code" | "document" | "design" | "report" | "other"
  format: string          // 文件格式，如".zip"、".pdf"
  description: string     // 交付物说明
}
```

### 6.5 Spec 确认流程

#### 6.5.1 雇主确认

1. Spec 提交后，雇主在 Marketplace Task 详情页看到 Spec 预览
2. 雇主可以逐条查看需求、验收标准、交付物清单
3. 雇主操作：
   - **确认签订** → Spec 锁定为 `spec_snapshot`（不可篡改的 JSON + hash），Project 状态 → "契约已签订"，自动进入 Phase 3
   - **不认可** → 填写不认可原因（可针对具体条目），触发 Agent 修订流程

#### 6.5.2 雇主超时未确认

**规则**：
- 默认超时：雇主选标后 **7 天**未确认 Spec → 自动取消 Project
- 催办节奏：第 3 天首次催办 → 第 5 天二次催办 → 第 7 天取消
- 取消后：
  - `Project` 状态 → **已取消**
  - 原中标 `Opportunity` 状态 → **中标失效**
  - `Marketplace Task` 重新开放竞标，并进入下一轮 `bid_round`
  - 上一轮竞标席位全部归档清零；新一轮席位从 `0 / seat_limit` 重新计算
  - 原 Workspace 若需再次参与，必须在**原 Opportunity** 上手动发起新一轮竞标
- 平台同步记录雇主超时行为，用于后续信誉体系评估

### 6.6 Project 状态机（Phase 2 部分）

```
雇主选标
   │
   ▼
┌──────────────┐

└──────┬───────┘
       │
       │ Spec 签约工作流执行并提交 Spec
       ▼
┌──────────────┐
│ 等待雇主确认   │ ◄── Spec 已提交，等待雇主操作
└──────┬───────┘
       │
  ┌────┼───────────────┐
  ▼    ▼               ▼
┌────────┐ ┌──────────────┐ ┌──────────────┐
│雇主确认 │ │ 雇主不认可     │ │ 超时未确认     │
└───┬────┘ └──────┬───────┘ └──────┬───────┘

## 第七章：自主规划交付（Phase 3）

### 7.1 概述

Spec 契约签订后，进入长任务业务的最后也是最长的一个阶段——**AI 自主规划、执行、交付**。这个阶段的核心挑战是：Agent Owner 不写死执行流程，而是让 AI 系统（Orchestrator Agent + 执行 Agent）根据每个 Project 的 Spec **动态生成执行计划**，然后自主按照计划执行、验证、交付。

与 Phase 1（竞标）和 Phase 2（签约）不同，Phase 3 面临的是一类完全不同的流程：
- Phase 1/2 的流程：**可预定义**（每个商机的竞标分析逻辑类似，每个 Project 的签约流程类似）
- Phase 3 的流程：**不可预定义**（"开发一个企业官网"和"写一份市场调研报告"的执行步骤完全不同）

因此 Phase 3 不能用"Agent Owner 预设工作流模板"，而是 **Orchestrator Agent 为每个 Project 动态生成 Plan → Agent Owner 审批 → 按 Plan 执行**。

### 7.2 Orchestrator Agent

#### 7.2.1 角色定义

Orchestrator Agent 是每个 Project 的"AI 项目经理"。它的职责是：

1. **分析 Spec**：深度理解 Spec 中的需求条目、验收标准、交付物清单
2. **生成执行 Plan**：将 Spec 转化为一个结构化的执行计划（DAG 图），包含需要创建的 Project Task 及其依赖关系
3. **分配执行者**：为每个 Project Task 分配合适的 Agent 或 Agent Team
4. **监控进度**：跟踪所有 Project Task 的状态，在 Task 失败时决定重试/重新分配/升级
5. **质量把关**：在每个里程碑节点触发 Evidence Gates 校验

#### 7.2.2 配置方式

Agent Owner 在 Workspace Settings 中设置默认 Orchestrator Agent。每个 Project 创建时继承此默认值，但 Agent Owner 可以为特定 Project 更换 Orchestrator。

#### 7.2.3 Orchestrator 异常处理

Orchestrator Agent 自身也可能执行失败（超时、Agent 不可用等）。处理规则：

- **Plan 生成超时**（默认 30min）→ Project 自动回到"契约已签订"状态，通知 Agent Owner
- Agent Owner 可手动触发重新生成 Plan，或更换 Orchestrator Agent 后重试
- Agent Owner 也可以跳过自动生成，**手动创建 Plan**（不依赖 Orchestrator）
- Plan 审批通过后 Orchestrator 失效不影响执行——编排引擎按已批准的 Plan DAG 推进，不依赖 Orchestrator 持续在线

### 7.3 Plan 生成与审批

#### 7.3.1 Plan 生成流程

1. **触发**：Project 状态变为"契约已签订"后，Orchestrator Agent 自动开始分析 Spec
2. **分析**：Orchestrator 阅读 Spec 的 requirements、acceptance_criteria、deliverables，理解任务的完整范围
3. **生成 Plan**：Orchestrator 输出一份结构化的执行计划，包括：
   - 需要创建哪些 Project Task（每个 Task 是一个独立的工作单元）
   - Task 之间的依赖关系（顺序依赖 / 可并行）
   - 每个 Task 的推荐执行 Agent（基于 Task 的 Skill 需求匹配）
   - 关键里程碑（Evidence Gate 检查点）
   - 预估时间线

4. **Plan 审批**：Plan 生成后，状态为"待审批"——**不自动执行**，必须等待 Agent Owner 审批。

#### 7.3.2 Plan 审批界面

Agent Owner 在 Workspace Console 中看到生成的 Plan，以 DAG 图形式展示（节点 = Project Task，边 = 依赖关系）。

**Agent Owner 可以做的操作**：
- ✅ **批准**：Plan 进入执行阶段
- ✏️ **编辑**：增删 Task 节点、修改依赖关系、更换执行 Agent、调整并行度
- 🔄 **重新生成**：要求 Orchestrator 重新分析 Spec 并生成新的 Plan（附修改意见）
- ❌ **驳回**：Plan 完全不可用，Agent Owner 手动创建一个新 Plan

**Plan 保存前的强制校验（平台代码执行）**：

无论是 Orchestrator 生成还是 Agent Owner 手动编辑的 Plan，在保存/提交审批前平台强制执行以下校验：

| 校验项 | 类型 | 处理 |
|--------|------|------|
| **DAG 无环性** | 硬校验（阻断保存） | 检测到循环依赖 → 拒绝保存，前端高亮显示循环节点集合（如 `Task A → Task B → Task C → Task A`），Agent Owner 必须修复后才能提交 |
| **依赖节点存在性** | 硬校验（阻断保存） | `depends_on` 中引用的 `task_id` 必须在同一 Plan 内存在 |
| **孤立节点** | 软警告（允许保存） | 存在无入边且无出边的节点（非起点/终点）→ 提示 Agent Owner 确认是否为设计意图 |
| **断裂节点** | 软警告（允许保存） | 存在无后继且非终点标记的节点 → 提示确认 |
| **子 Task 层级** | 硬校验 | 层级不超过平台上限（§7.4.3） |

**【设计理由】** DAG 无环性是硬性技术约束（否则执行引擎会死循环），必须阻断；孤立/断裂节点可能是设计意图（如可选扩展点），只警告不阻断。

#### 7.3.3 Plan 结构

一个 Plan 是 Project Task 的有向无环图（DAG）：

```
Plan {
  plan_id: string
  project_id: string
  version: int
  status: "pending_review" | "approved" | "executing" | "completed" | "rejected"
  tasks: array of PlanTask
  edges: array of Dependency
  generated_by: agent_id       // Orchestrator Agent
  approved_by: user_id         // Agent Owner
  created_at: datetime
  approved_at: datetime
}

PlanTask {
  task_id: string              // 对应 Project Task 的 ID
  title: string                // 如"需求分析：用户登录模块"
  description: string          // 详细工作说明
  assigned_agent_id: string    // 推荐执行 Agent
  estimated_effort: string     // 预估工时（如"2h"）
  milestone: boolean           // 是否为里程碑节点（触发 Evidence Gate）
  depends_on: [string]         // 依赖的 task_id 列表
}

Dependency {
  from: string                 // 前置 task_id
  to: string                   // 后置 task_id
  type: "sequential" | "conditional"  // 顺序依赖 or 条件依赖
}
```

### 7.4 Project Task 执行模型

#### 7.4.1 Project Task 是什么

Project Task 是 Plan 中的最小执行单元。它类比于 Jira/TAPD 中的 Issue——每个 Task 有明确的负责人（Agent）、输入、输出、状态。

**Project Task 与 Agent 的关系**：
- 一个 Project Task 分配给 **一个 Agent**（或一个 Agent Team）
- Agent 自主完成该 Task（阅读上下文 → 执行工作 → 产出交付物 → 更新状态）
- Agent 可以在自己的 Project Task 下创建**子 Task**（类似 Jira 的 sub-task），进一步拆解复杂工作

#### 7.4.2 Project Task 生命周期

```

       │
       ▼
┌──────────┐
│  待开始   │ ◄── 依赖的 Task 尚未全部完成
└─────┬────┘
      │ 依赖满足
      ▼
┌──────────┐
│  可执行   │ ◄── 等待 Agent 领取
└─────┬────┘
      │ Agent 领取
      ▼
┌──────────┐
│  执行中   │ ◄── Agent 正在工作
└─────┬────┘
      │
  ┌───┼───┐
  ▼   ▼   ▼
┌──┐┌──┐┌──────────┐
│完││失││  已暂停   │ ◄── Agent Owner 干预暂停
│成││败│└─────┬────┘
└──┘└──┘      │
  │   │       ▼
  │   │  ┌──────────┐
  │   │  │  执行中   │（恢复后继续）
  │   │  └──────────┘

  │   └──► 重试（自动）或 重新分配 Agent（手动）或 标记 Project 异常
  │

#### 7.4.3 子 Task 机制

Agent 在执行 Project Task 时，如果发现任务过于复杂，可以自行创建子 Task 来拆解工作。子 Task 继承父 Task 的 Agent 分配，记录在同一个 Project 下。

**子 Task 层级上限**：最多 3 层（Project Task → Sub-task → Sub-sub-task），防止无限拆解。**平台代码强制执行**——Agent 通过 MCP 工具 `create_subtask` 创建子 Task 时，平台校验 `depth < 3`，超限则拒绝并返回错误。

**为什么要子 Task**：
- 这是白话文稿中明确提到的设计——类比人类在 Jira 中给自己建子任务
- 子 Task 让 Agent 的工作过程**可追踪**（Agent Owner 能看到 Agent 做了什么、做到哪了）
- 子 Task 的产物（附件、评论）自然成为交付物的一部分

### 7.5 质量保障：多层可靠性栈

**【核心章节】** 本章节是对 §5.5.1 中提出的"流程编排不能单独解决 Agent 稳定性"的系统性回答。

CSI 的 Phase 3 质量保障不是靠 Agent "听话"，而是靠四层机制叠加：

```
┌──────────────────────────────────────────────┐
│ L4: Human 干预 + 纠纷升级                      │
│     所有自动化手段耗尽后的最终保障                │
├──────────────────────────────────────────────┤
│ L3: Harness Loop（有界重试 + 上下文增强）       │
│     Agent 输出不合格 → 自动重试，最多 N 次       │
├──────────────────────────────────────────────┤
│ L2: Evidence Gates（结构化校验点）              │
│     JSON Schema / 字段完整性 / 验收标准逐项匹配   │
├──────────────────────────────────────────────┤
│ L1: 确定性执行框架（编排引擎强制执行）            │
│     超时检测 / 状态机推进 / MCP 工具拦截校验      │
└──────────────────────────────────────────────┘
```

#### 7.5.1 L1：确定性执行框架

这一层是**平台代码**，不含任何 AI 不确定性。它是 Agent 执行环境的"沙盒边界"。

| 机制 | 做什么 | 为什么是确定的 |
|------|--------|:---:|
| **MCP 工具拦截** | 编排引擎在 Agent 进程外监听 MCP 工具调用。Agent 调用 `submit_for_review` 时，引擎拦截并校验参数 | 引擎代码执行，非 Agent 决策 |
| **超时检测** | 每个 Agent 节点有最大执行时间。超时 → 引擎强制终止，进入 L3 重试 | 定时器是确定性的 |
| **状态机强制推进** | Agent 完成后，引擎**强制**推进 Project Task 状态。Agent 不能跳过状态 | 状态转移规则是确定性的 |
| **API 调用** | 工具节点调平台 API（如提交交付物到雇主侧）——100% 由平台代码执行 | Agent 不直接调 API |

**为什么 POC 阶段缺了这一层**：POC 中是 Agent 自己调 CLI/API——Agent 忘了调、调错了，系统不知道。L1 的核心思想是：**不是 Agent 调 API，而是编排引擎调 API，Agent 只负责产出内容**。

具体而言——Agent 调用 `submit_for_review` 这个 MCP 工具时发生了什么：

```
Agent 进程内:                     编排引擎（Agent 进程外）:
                                  │
  Agent: "我需要提交交付物"        │
  调用 MCP 工具:                   │
  submit_for_review({             │
    deliverables: [...]           │
  })                              │
       │                          │
       └──────────────────────────► 拦截 MCP 调用
                                  │
                                  ├─ 校验 JSON Schema ✓
                                  ├─ 校验 deliverables 非空 ✓
                                  ├─ 校验文件存在（MinIO） ✓
                                  ├─ 推进 Project Task 状态
                                  ├─ 调用平台 API 通知雇主
                                  └─ 返回成功给 Agent
```

Agent 不调这个工具？编排引擎在超时后判定失败。Agent 调了但参数不对？编排引擎校验 JSON Schema 后返回错误，Agent 修正。**Agent 的唯一职责是"决定何时提交 + 提交什么内容"，而"提交是否有效"由平台代码判定。**

#### 7.5.2 L2：Evidence Gates（平台确定性校验 + Agent 质检环节）

Evidence Gates 分为两部分：**平台自动执行的确定性校验**（G1/G2/G3/G6）和 **Plan 中编排的 Agent 质检环节**（G4/G5）。

##### 平台确定性校验（G1/G2/G3/G6 — 100% 代码执行）

这几个 Gate 是纯数据对比，平台代码在里程碑 Task 完成后自动运行，不依赖任何 AI 判断：

| Gate | 检查内容 | 检查方式 | 为什么是确定的 |
|------|---------|---------|:---:|
| G1 需求覆盖 | 每个 Spec `requirement` 是否有对应的产出物声明？ | 遍历 Spec.requirements，检查每条的 `requirement_id` 是否在 deliverables 关联列表中 | 纯数据遍历对比 |
| G2 验收标准 | 每个 `acceptance_criterion` 是否有验证记录？ | 遍历 Spec.acceptance_criteria，检查每条是否在 Agent 提交的 verification_results 中有对应记录 | 纯数据匹配 |
| G3 交付物完整性 | `deliverables` 列表中的文件是否全部存在？ | MinIO 文件存在性检查（HEAD 请求） | 文件系统操作 |
| G6 流程合规 | Plan DAG 中所有必需节点是否已执行？ | 遍历 Plan.tasks，检查 milestone=true 的节点 status 是否全部 = 完成 | DAG 遍历 |

**Gate 结果处理**：
- 全部 Pass → 推进到下一阶段
- 部分 Fail → 生成失败报告（明确指出哪个 Gate 失败、缺失了什么），Agent 收到反馈后修复 → 重新提交 → 再次 Gate
- 连续 3 次 Gate Fail → 升级到 L4（Human 干预）

**Gate 执行方式**：
- G1/G2/G3/G6 **同步执行**（秒级数据对比），Agent 调用 `submit_for_review` 时编排引擎即时校验，Agent 实时拿到结果
- 执行 Agent 提交后由平台代码立即跑 Gate，Agent 等待结果


##### Agent 质检环节（G4/G5 — 流程编排中的 Agent 节点）

G4（Spec 合规）和 G5（交付物质量）**不是平台能统一做确定性校验的**——每个项目类目不同，验证方式就不同。例如：
- "企业官网"项目：需要 Reviewer Agent 检查页面是否符合设计 Spec、Tester Agent 在不同浏览器上验证
- "市场调研报告"项目：需要 Reviewer Agent 检查报告结构、数据引用准确性
- "Python 库开发"项目：执行 Agent 自跑 `pytest` + `mypy` 做自测

因此 G4/G5 的正确做法是：**在 Plan 编排中，由 Agent Owner 或 Orchestrator 配置 Reviewer Agent、Tester Agent 等质检节点，Agent 自主选择合适的验证工具执行。** 这正是 CSI 靠流程编排来保障质量的核心体现。

**Plan 中的典型质检编排**：

```
[执行 Agent: 完成开发 Task]
       │
       ▼
[执行 Agent: 自测] ── Agent 自己跑 lint/tsc/pytest/自查，输出自测报告
       │
       ▼
[条件判断: 自测通过?]
       │
  ┌────┴────┐
  ▼         ▼
[是]       [否] → 回到执行 Agent 修复
  │
  ▼
[Reviewer Agent: Spec 合规检查] ── 对照 Spec 逐条审查产出物，输出审查报告
       │
       ▼
[条件判断: 审查通过?]
       │
  ┌────┴────┐
  ▼         ▼
[是]       [否] → 回到执行 Agent 修复（带审查意见）
  │
  ▼
[Tester Agent: 功能验证] ── 实际运行/测试交付物，输出测试报告
       │
       ▼
[条件判断: 测试通过?]
       │
  ┌────┴────┐
  ▼         ▼
[是]       [否] → 回到执行 Agent 修复（带测试失败详情）
  │
  ▼
[里程碑节点: 触发 G1/G2/G3/G6 平台校验]
       │
       ▼
  进入下一阶段
```

**G4/G5 质检节点的关键规则**：
- 质检 Agent（Reviewer/Tester）只能**读**执行 Agent 的产物，不能修改——保证职责分离
- 质检结果（审查报告、测试报告）是结构化输出，存入 Project Task 的 `evidence_gate_results` 字段
- 质检节点本身也是 Agent 节点，也可能失败——失败时进入 Harness Loop（L3）
- Agent Owner 在审批 Plan 时可以看到 Orchestrator 编排的质检流程，可增删 Reviewer/Tester 节点

#### 7.5.3 L3：Harness Loop（有界重试）

当 L1 超时检测触发或 L2 Gate 校验失败时，编排引擎进入 Harness Loop。

**Loop 机制**：

```
第 1 次尝试: Agent 执行
  ├─ 失败 → 收集失败信息（错误日志、未通过 Gate 列表）
  │
  ▼
第 2 次尝试: Agent 重新执行（注入 4 段结构化上下文，见下方）
  ├─ 失败 → 增强反馈，调整策略
  │
  ▼
第 3 次尝试: Agent 重新执行（更直接的指令 + 可能更换 Agent）
  ├─ 失败 → 最后一次机会
  │
  ▼
第 4 次尝试: Agent 重新执行（降低难度/缩小范围）
  ├─ 失败 → 升级到 L4（Human 干预）
  │
  ▼
 成功 → 通过 L2 Gate → 推进
```

**Harness Loop 重试上下文结构（4 段式，平台代码组装注入）**：

每次重试时，编排引擎按以下**固定 4 段结构**组装 Prompt 上下文注入 Agent：

```
[ORIGINAL TASK]
  - 原始 Project Task 描述
  - 关联 Spec 片段（requirements / acceptance_criteria / deliverables）

[PREVIOUS ATTEMPT]
  - 上一次 Agent 输出快照（含中间产物 workspace 文件清单与关键内容）
  - 仅保留最近 1 次快照（避免上下文膨胀，控制 Token 成本）

[FAILURE REPORT]
  - 结构化 JSON：{gate_id, failed_criteria[], evidence, error_log}
  - 明确列出未通过的 Gate 编号、未满足的验收标准、失败证据引用

[FIX INSTRUCTION]
  - 模板化指令："你必须修复以下问题：{failed_criteria}，参考 {evidence}"
  - 允许 Agent Owner 在 Console 中追加自定义修复提示
```

**关键设计**：
- **有界**：默认 4 次，Agent Owner 可配置（2-6 次）。不能无限重试——既消耗资源，也在做无用功
- **上下文增强**：每次重试不是"重新来一遍"，而是带着上一次的失败反馈。Agent 知道"我哪里做错了"
- **快照仅保留最近 1 次**：`[PREVIOUS ATTEMPT]` 段仅注入最近一次的产物快照，历史失败信息由 `[FAILURE REPORT]` 段以结构化摘要形式承载
- **Workspace 文件保留**：重试时保留上一次的文件/产物，Agent 可以在上次基础上修正，而不是从零开始
- **可更换 Agent**：第 3 次重试时可选择换一个 Agent 执行（不同 Agent 可能擅长不同的修正方式）

#### 7.5.4 L4：Human 干预

当 L3 Harness Loop 耗尽所有重试次数后，Project Task 进入"需人工干预"状态，通知 Agent Owner。

**三级干预模型**（白话文稿中定义）：

| 级别 | 描述 | 触发场景 | Agent Owner 操作 |
|------|------|---------|-----------------|
| **L1 轻量** | Agent 请求确认/建议 | Agent 在执行中遇到不确定的决策 | 回复建议或确认，Agent 继续 |
| **L2 暂停** | Agent 暂停等待指示 | Agent 遇到关键阻塞（如缺少必要信息） | Owner 提供信息/决策，恢复执行 |
| **L3 干预** | 系统自动暂停，需人工接管 | Harness Loop 耗尽、Gate 连续失败 | Owner 审查整个 Task 上下文，手动处理或关闭 |

**L3 干预的具体操作**：
- 查看 Agent 的完整执行日志和产物
- 直接与 Agent 对话（通过 Comment 机制）来引导修正
- 手动完成该 Task（Agent Owner 自己做，然后标记完成）
- 关闭该 Task（承认无法完成，触发 Project 级别的异常流程）
- 重新分配 Task 给另一个 Agent

### 7.6 Goal Mode（目标模式）

除了 Spec 规定的显性需求外，Orchestrator Agent 在执行过程中可能发现 Spec 未覆盖但客观需要的工作。Goal Mode 允许 Agent 在执行达标的基础上，**自主判断是否需要超越 Spec 做更好的交付**。

**Goal Mode 行为**：
- Agent 判定当前产出已满足 Spec 最低要求
- Agent 评估："如果我再做 X，交付质量会显著提升"
- Agent **不能自动执行 X**——必须先在 Project 中提出建议
- Agent Owner 审核：批准（Agent 继续做 X）/ 驳回（按 Spec 交付即可）

**Goal Mode 的约束**：
- Goal Mode 的额外工作必须在 Spec 范围内（不能 scope creep）
- **20% 工时阈值口径**：
  - **基准**：整个 Project 的 Plan 预估总工时（在 Plan 生成时确定并写入 `plan.estimated_total_effort`，锁定不变）
  - **计算方式**：Goal Mode 额外工作累计消耗工时 / Plan 预估总工时 ≥ 20% → 自动触发强制暂停
  - 平台按 Project 维度实时累计 Goal Mode 额外工时
- **达阈处理**：Project 状态保持"执行中"，但所有 Goal Mode 分支任务暂停；通知 Agent Owner 审批
  - Owner 批准继续 → Goal Mode 额度重置为 0，可继续累计（相当于追加一个 20% 额度）
  - Owner 停止 Goal Mode → 回到 Spec 范围完成交付
- Goal Mode 成果不计入验收标准（不是雇主必须验收的部分），但可作为"增值交付"

**【设计理由】** 单 Task 级 20% 阈值过严会频繁打断执行；Project 级 20% 给 Agent 更大自主空间，同时保住 Agent Owner 的成本上限（配合 §7.12 计算预算上限双重兜底）。

### 7.7 交付与验收

#### 7.7.1 交付物提交流程

1. Plan 中所有 Project Task 完成 + 全部 Evidence Gates 通过
2. Orchestrator Agent 汇总所有交付物，生成《交付报告》
3. Agent 调用 MCP 工具 `submit_deliverables`，将交付物提交到雇主 Marketplace Task 下
4. Project 状态 → "待验收"

#### 7.7.2 雇主验收

雇主在 Marketplace Task 详情页看到：
- 交付物列表（文件可下载/预览）
- 交付报告（AI 生成的交付说明）
- Spec 验收标准逐项对照表（哪些满足、哪些待确认）

**雇主操作**：
- **验收通过** → Project 状态 → "已完成"，进入结算流程
- **要求修订** → 填写修订原因（可针对具体验收标准），仅限 **Spec 既有范围内未达标项** 的修正；若属于新增需求/扩大范围，则转 §9.6 Spec 变更流程

#### 7.7.3 修订循环

```
雇主要求修订
       │
       ▼
Orchestrator 分析修订原因，判断影响范围
       │
  ┌────┴────┐
  ▼         ▼
[局部修订]  [大范围修订]
  │         │
  ▼         ▼
创建新     Orchestrator 生成修订 Plan
Project     → Agent Owner 审批
Task        → 执行修订
  │         │
  └────┬────┘
       ▼
重新提交交付物
       │
       ▼
雇主再次验收
```

**修订次数**：Spec 中约定的 `revision_limit`（默认 2 次）。超过修订次数后：
- 当前修订流程暂停，Project 状态 → **修订协商中**（新增子状态，隶属"待验收"大类）
- 进入 **2 天协商窗口**，双方可选以下 4 个结构化选项：

| 选项 | 发起方 | 需对方同意 | 结果 |
|------|--------|-----------|------|
| A. 追加修订次数 | 雇主 | Agent Owner 同意 | 追加 2 次修订额度，Project 回到"待验收"，继续修订循环 |
| B. 转 Spec 变更（付费） | 雇主 | Agent Owner 同意 | 走 §9.6 Spec 变更流程（可能加价 + 延期） |
| C. 接受当前交付 | 雇主 | 无需 | 强制验收通过，Project → "已完成"（雇主评价环节可给差评） |
| D. 发起纠纷 | 任一方 | 无需 | Project → "纠纷处理中"，走 §9.7 平台仲裁 |

**协商窗口超时规则**：
- 2 天窗口内**无任何操作** → **默认执行 C（接受当前交付）**
- 默认接受后保留 **7 天售后申诉期**：雇主可在此期间对交付质量问题发起纠纷申诉；申诉不影响 Agent Owner 已产生的记录，但若纠纷成立可从平台保证金扣除赔付
- 协商窗口内任一方选择 D → 立即进入纠纷处理，不等待剩余时间

**【设计理由】** 结构化 4 选项避免自由文本沟通中的扯皮；默认 C 保护 Agent Owner 的劳动成果（不能因雇主沉默博弈无限拖延 Project），同时用 7 天售后期兜底雇主的合理权益。

### 7.8 Agent Owner 的监控与干预

Agent Owner 在 Phase 3 不是完全被动的——他可以看到 Project 的实时进展并在需要时介入。

**监控视图**（Workspace Console → Project 详情页）：
- Plan DAG 图，每个 Task 节点颜色标识状态（待开始/执行中/完成/失败）
- 当前执行中的 Task 的 Agent 活动日志（实时 comments 流）
- Evidence Gate 结果
- 交付物预览

**主动干预操作**：
- 在任何暂停/执行中的 Task 上发起对话（通过 Comment 与 Agent 交流）
- 暂停/恢复 Task 执行
- 重新分配 Task 给另一个 Agent
- 手动关闭 Task

**边界约束**：
- Agent Owner **不可单方面关闭 Project**
- Project 的结束只能通过：雇主验收完成、协商取消达成一致、平台仲裁关闭、或系统规则触发（如 Spec 超时自动取消）

### 7.9 通知机制

CSI 平台通知按紧急程度分为三级：

| 级别 | 渠道 | 典型场景 |
|------|------|---------|
| **信息级** | Inbox（站内） | 商机投递、竞标结果、Project 状态变更、Task 完成 |
| **提醒级** | Inbox + 邮件 | Spec 待确认（雇主）、Human 审批待处理、雇主催办通知 |
| **紧急级** | Inbox + 邮件 + App Push | L4 干预触发、Harness Loop 耗尽、雇主超时即将自动取消/验收、Runtime 离线超宽限期 |

**通知聚合**：同一 Project 同一类型的事件在短时间内（1h）多次触发时合并为一条通知（如"Project xxx 有 3 个 Task 进入 L4 干预"），避免刷屏。

### 7.10 Agent Team（团队协作模式）

**【设计要点】** 白话文稿提到 Agent Team 节点。当前 PRD 定义以下 Team 模式：

#### 7.10.1 Team 类型

| 类型 | 描述 | 适用场景 |
|------|------|---------|
| **Leader-Delegation** | Team Leader Agent 接收 Task → 分析 → 拆分 → 委派给成员 Agent → 汇总结果 | 复杂 Task 需要多种技能（如"开发 + 测试"） |
| **Peer Review** | 两个 Agent 独立执行同一 Task → 对比结果 → 合并最优方案 | 对质量要求极高的 Task |
| **Pipeline** | 多个 Agent 按顺序处理：A 产出 → B 检查/增强 → C 最终输出 | 需要多道工序的任务 |

#### 7.10.2 Team 配置

Agent Owner 在 Workspace 中预先创建 Agent Team：
- 指定 Team Leader Agent
- 添加成员 Agent
- 选择默认协作模式

Project Task 分配到 Team 时，Team Leader 根据 Task 内容和成员能力决定实际分工。

#### 7.10.3 Team 模式下的 Harness Loop 计数

**核心规则**：Harness Loop 的失败尝试次数计数在 **Team 层级**（默认 3 次，与单 Agent 一致），不按成员 Agent 单独计数。

**Leader-Delegation 模式**：
- Team Leader 委派给成员 Agent A 执行失败 → 视为 Team 整体 1 次失败尝试
- Team Leader 在 Harness 预算内**有权重新分配**给成员 Agent B 重试 → 视为下一次尝试（消耗一次预算）
- 超过 Team 层级 Harness 上限 → 整个 Team 视为失败，升级到 L3/L4（Human 干预）

**Peer Review 模式**：
- 两个 Agent 独立执行；若合并结果 Gate 校验失败 → 计 1 次 Team 失败尝试

**Pipeline 模式**：
- 任一环节失败 → 计 1 次 Team 失败尝试；Leader 可选择回退到失败环节重试或整条流水线重来

**【设计理由】** Team 内部调度是 Leader 的职责，Leader 有权重新分配成员；但不能因内部无限重试拖累整个 Project 的可靠性预算——外部看 Team 与单 Agent 应遵守同样的失败预算。

### 第七章关键确认点

在推进后续章节之前，请确认以下 3 个关键点：

**【已确认】Agent Team 模式**：公测版只做 **Leader-Delegation**（与 Multica Squad 模式对齐，可直接基于 Multica 源码改造或参考实现）。Peer Review 和 Pipeline 模式后续迭代。

**【已确认】修订次数**：严格遵守 Spec 约定的 `revision_limit`。交付物提交验收前必须确保质量——必要时 Agent Owner 可在 Plan 中"提交验收"节点前添加 **Human 验收节点**，由 Owner 先行内部审核，确认符合 Spec 后再提交雇主验收。这关乎 Workspace 的品牌信誉。

### 7.12 Project 计算预算上限（成本风控）

**背景**：AI 平台最大的运营风险之一是"跑飞的 Agent"消耗巨额 LLM API 费用和 Runtime 运行时间——尤其在 Goal Mode 和 Harness Loop 场景下。计算预算上限是 Agent Owner 的止损保险，也是平台的信誉保障。

**配置位置**：Workspace Settings → "Project 计算预算上限"

| 配置项 | 默认值 | 可选范围 | 说明 |
|--------|--------|---------|------|
| `project_compute_budget_ratio` | **报价的 30%** | 10% - 80% | Project 允许消耗的最大计算成本占该 Project 报价的比例 |
| `budget_alert_threshold` | 80% | 50% - 95% | 达到该比例时向 Agent Owner 发送提醒级通知 |

**计算成本口径**（平台按 Project 维度实时累计）：
- LLM Token 消耗成本（按当期平台采购价换算）
- Runtime 计算时间成本（按 Pod 资源占用时长换算）
- 平台按 Project 事件流实时归集，Agent Owner 在 Console 可见"预算消耗进度条"

**触发规则**：

| 消耗比例 | 系统行为 |
|---------|---------|
| ≥ 80%（提醒阈值） | 发送**提醒级**通知给 Agent Owner："Project xxx 已消耗预算 80%，请关注" |
| ≥ 100% | Project 状态 → **预算超限暂停**（Phase 3 新增子状态，隶属"已暂停"）；所有执行中 Task 立即暂停；发送**紧急级**通知给 Agent Owner |

**Agent Owner 处理选项（预算超限暂停后）**：
- **A. 增加预算继续**：手动追加预算额度，Project 恢复"执行中"
- **B. 优化 Plan 后继续**：Agent Owner 审查 Plan，裁剪冗余 Task 或换更廉价的 Agent 后恢复执行
- **C. 放弃并进入协商取消**：Project → **协商取消中**（走 §9.6.1 流程与雇主协商）

**边界与联动**：
- 该上限与 §7.6 Goal Mode 20% 工时阈值**双重兜底**——先触发哪个走哪个
- 预算超限暂停**不影响**已生成交付物；恢复执行时从暂停点继续
- 该配置为 Workspace 级默认值，特殊 Project 可由 Agent Owner 手动覆盖

**【设计理由】** 报价的 30% 作为默认值是 AI 交付业务的合理毛利保护线；给 Agent Owner 完整的止损选项（增预算/优化/取消），避免"跑飞成本"直接吃掉利润；同时用"预算超限暂停"作为独立状态便于运营监控。

## 第九章：异常与边界场景

### 9.1 Agent Runtime 离线

**场景**：正在执行 Project Task 的 Agent 突然离线。

**处理**：
1. Runtime 心跳超时（90s）→ 宽限期（5min）
2. 宽限期内恢复 → Task 继续执行
3. 宽限期超时 → Task 标记为"失败"，进入 Harness Loop 重试
4. Harness Loop 重试时可分配到同一 Runtime 的其他在线 Agent，或等待 Runtime 恢复

### 9.2 Agent 执行超时

**场景**：Agent 执行时间超过 Task 的预估时间阈值。

**处理**：
1. 编排引擎检测超时 → 发送警告（仍可继续）
2. 超过阈值 2 倍 → 强制终止 Agent 进程，Task 标记失败，进入 Harness Loop
3. Harness Loop 重试时给予更明确的时间约束指令

### 9.3 Agent 输出不符合预期

**场景**：Agent 完成了执行，但输出不满足校验要求。

**处理**：
- JSON Schema 校验失败 → L2 Gate 直接拦截，返回错误 → Agent 修正（不计入 Harness 次数，因为这是格式问题不是质量失败）
- Evidence Gate 失败 → 进入 Harness Loop（计 1 次尝试）
- 连续 3 次 Gate 失败 → 升级 L4

### 9.4 雇主长期不响应

**场景汇总**：

| 阶段 | 场景 | 超时 | 处理 |
|------|------|------|------|
| Phase 1 | 雇主发布任务后不选标 | 任务有效期（平台默认 30 天） | `Marketplace Task → 已过期`；所有关联非终态商机 → 已过期 |
| Phase 1 | 席位满后不选标/驳回 | 72 小时 | 详见 §5.3；`Marketplace Task` 保持招标中，`bid_round += 1`，席位清零 |
| Phase 2 | 雇主选标后不确认 Spec | 7 天 | `Project → 已取消`；`Opportunity → 中标失效`；`Marketplace Task → 进入下一轮并重新开放竞标`；上一轮席位归档清零；扣雇主信誉分 |
| Phase 3 | 雇主收到交付物不验收 | 14 天 | 满足全部条件自动验收（详见下方细则） |

**Phase 3：14 天自动验收细则**

**自动验收成立的三条硬约束**（必须**同时**满足）：
1. 所有平台确定性 Gate（G1/G2/G3/G6）全部通过
2. 平台已按下述节奏发送 3 次催验收通知
3. 距 Agent 提交交付物（Project 进入"待验收"）已满 14 天自然日

**催办时间点与级别**（自 Project 进入"待验收"起计时）：

| 时点 | 级别 | 渠道 | 文案要点 |
|------|------|------|---------|
| 第 5 天 | 信息级 | 站内 Inbox + 邮件 | "您有待验收的交付物，请及时处理" |
| 第 9 天 | 提醒级 | 站内 + 邮件 + 短信 | "还剩 5 天将自动验收通过" |
| 第 13 天 | 紧急级 | 站内 + 邮件 + 短信 + App Push | "24 小时内未操作将自动验收通过" |
| 第 14 天 24:00 | — | 系统执行 | 满足全部条件 → **自动验收通过** |

**自动验收后**：
- Project 状态 → **已完成**；`Marketplace Task → 已完成`（附录 D 联动）
- 保留 **7 天售后申诉期**：雇主可在此期间发起纠纷申诉
  - 申诉不阻断 Agent Owner 的正常收款流程
  - 纠纷成立时按平台仲裁结果从平台保证金/后续结算中扣除赔付
  - 7 天后未申诉视为最终认可
- 若条件（1）未满足（存在未通过的 G1/G2/G3/G6）→ **不自动验收**，Project 保持"待验收"，等待 Agent Owner 修复交付质量后再启动 14 天计时（交付质量本身不达标不应自动验收）

### 9.5 并发竞标与选标冲突

**场景**：雇主正在查看竞标方案时，竞标席位被新的竞标填满。

**处理**：
- 雇主侧看到的竞标列表是实时快照（可能短暂不一致）
- 选标操作以数据库当前状态为准
- 如果雇主尝试选标时目标商机已被驳回/过期 → 提示"该竞标已失效"

### 9.6 Spec 签订后雇主想改需求

**场景**：Spec 已签订，但雇主在执行过程中提出新需求。

**处理**：
- 新需求 ≠ Spec 规定的修订（revision 是针对 Spec 范围内约定的交付内容的修正）
- **修订**：仅针对既有 `requirement` / `acceptance_criterion` / `deliverable` 的补齐、修正、返工，不新增范围
- **新需求/范围扩大**：新增功能、增加新的验收标准、扩大原边界、增加新的交付物，均视为 Spec 变更
- 新需求需要走 **Spec 变更流程**：雇主发起变更请求 → Orchestrator 评估影响 → 给出新报价/新时间 → 雇主确认 → 生成新版本 Spec → 调整 Plan
- Spec 变更版本号递增（v1 → v2），原 Spec v1 快照保留（防扯皮）
- 这是"Phase 2 的延续"，不是在 Phase 3 随便改

**"修订 vs 新增需求"判定机制（24 小时结构化流程）**：

雇主发起"要求修订"后，Agent Owner 必须在 **24 小时**内在 Console 中做出以下二选一：

| 选项 | 操作 | 后续流程 |
|------|------|---------|
| A. 接受为"修订" | Agent Owner 判定该请求在 Spec 既有范围内 | 按 §7.7 修订流程处理，占用 `revision_limit` |
| B. 标记为"新增需求" | Agent Owner 判定该请求超出 Spec 范围 | 系统推送该判定给雇主，雇主二次确认 |

**雇主二次确认（B 选项后）**：
- 雇主同意为"新增需求" → 转 §9.6 Spec 变更流程（可能加价 + 延期）
- 雇主不同意 → 双方进入 **24 小时协商窗口**（可在 Project 讨论区沟通）
- 协商无果 → Project → **纠纷处理中**，由平台裁定

**Agent Owner 24 小时超时未响应** → **默认接受为"修订"**（保护雇主权益，避免 Agent Owner 用"这是新增需求"当挡箭牌拖延交付）

**【设计理由】** Agent Owner 有专业判断权（是否超范围），但雇主对"付不付新钱"有最终决定权；平台通过 24 小时超时默认+纠纷兜底避免长期扯皮。

- 若雇主与 Agent Owner 对"这是修订还是新增需求"始终判断不一致 → Project 状态进入"纠纷处理中"，由平台裁定

### 9.6.1 雇主中途取消 Project

**场景**：Project 处于执行中或待验收，雇主想取消（如自身需求变化）。

**处理**：
- 公测版**不允许雇主单方面取消**（保护 Agent Owner 权益——AI 已投入计算资源和时间）
- 雇主可发起"协商取消"请求 → Project 状态进入 **协商取消中**
- Agent Owner 需在 **3 天**内响应：同意取消 / 拒绝取消 / 提出部分结算方案

**Agent Owner 3 天内正常响应的分支**：
- 同意取消且双方对结算金额已达成一致 → Project → **已取消**
- 提出部分结算方案 → Project 保持 **协商取消中**，等待雇主确认；雇主需在 **3 天**内确认或拒绝
- 主动拒绝取消 → Project 回到"执行中"或"待验收"（视原状态）

**Agent Owner 3 天内未响应的分支（按 Project 阶段区分）**：

| 原 Project 阶段 | 判定 | 处理 |
|----------------|------|------|
| **执行中**（交付物尚未提交） | 视为同意取消 | 按已完成 Project Task 对应里程碑权重**自动部分结算**；结算完成 → Project → **已取消** |
| **待验收**（交付物已提交） | 视为拒绝取消 | Project 回到 **待验收**，走正常验收/修订流程；Agent Owner 已交付成果不应因未响应而白干 |

**里程碑部分结算规则**：
- 仅结算 Spec 中定义了权重、且当前状态为"验证通过"的 Project Task 对应的报价份额
- 例：Spec 定义 3 个里程碑权重 30%/40%/30%，已完成第 1、2 个 → 结算 70% × 报价
- 若不存在任何"验证通过"且带权重的里程碑 → Project → **纠纷处理中**，由平台裁定

**雇主对 Agent Owner 部分结算方案 3 天内未响应**：
- 若存在**已验证通过的可结算里程碑** → 按 Agent Owner 提出的方案自动结算，Project → **已取消**
- 若不存在可客观结算的里程碑 → Project → **纠纷处理中**

**双方对取消或部分结算无法达成一致** → Project → **纠纷处理中**，平台介入仲裁

**说明**：
- `协商取消中` **不适用 §9.4 的自动验收规则**；自动验收仅适用于交付物已正式提交且未进入协商取消/纠纷流程的场景
- 为降低取消争议，Spec 生成阶段应尽量拆分带权重的可结算里程碑；未拆分的长任务在协商失败时更易进入平台仲裁

### 9.7 Agent Owner 中途退出

**场景**：Project 执行中，Agent Owner 注销账号或关闭 Workspace。

**处理**：
- 正在执行的 Project 暂停，通知雇主
- 已产生的交付物归属于雇主（雇主可以带走，找其他 Workspace 继续）
- 未完成的结算按平台规则处理
- 若 Agent Owner 是被动关闭（违规封禁等），平台介入仲裁

## 附录 D：全实体状态机单一真相表

本附录是全文所有状态机的**单一权威口径**。研发在实现枚举、状态机、审计事件时，均以本附录为准。若正文（§5.4 / §6.6 / §7.4.2 / §7.11 / §8.7 / §9.4 等）与本附录出现枚举名或转移规则冲突，一律以本附录为准，并回头修正正文。

### D.1 Marketplace Task 状态机

| 状态 | 含义 | 进入条件 | 可执行操作 | 是否终态 |
|------|------|---------|-----------|:--------:|
| 待发布 | 雇主草稿，未提交 | 雇主创建任务 | 提交发布 / 删除 | 否 |
| 招标中 | 已发布，接受竞标 | 提交发布 / 全部驳回后重开 / Spec 超时后重开 | 选标 / 全部驳回 / 到期关闭 | 否 |
| 已选标 | 雇主已选中某个竞标方案 | 雇主选标操作 | 联动 Project 创建 | 否 |
| 已完成 | 关联 Project 验收通过 | Project → 已完成 | — | 是 |
| 已过期 | 有效期到达时仍未选标 | 有效期到达 | — | 是 |
| 已关闭 | 雇主主动关闭 / 平台强制关闭 | 雇主关闭 / 平台运营干预 | — | 是 |
| 已取消 | 关联 Project 进入终态"已取消"或"已关闭"，且无后续竞标可能 | Project → 已取消/已关闭 且不再重开 | — | 是 |

**多轮竞标语义**：Marketplace Task 内含 `bid_round` 字段。每次任务重新开放竞标（雇主全部驳回、Spec 超时后重开），`bid_round += 1`，上一轮席位归档清零，新一轮席位从 `0 / seat_limit` 重新累计。

**Marketplace Task 关键时间字段（v0.3 新增）**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `seat_limit` | int | 竞标席位上限，雇主发布时设置 |
| `seat_taken` | int | 当前 bid_round 已占用席位数 |
| `expires_at` | datetime | 任务有效期到达时间（进入"已过期"的触发时点） |
| `seat_full_deadline` | datetime (nullable) | 席位满 72 小时倒计时截止时间（席位达 `seat_limit` 时自动写入，见 §5.3） |
| `seat_full_locked_at` | datetime (nullable) | 席位满触发倒计时的时刻，用于定时任务与前端展示 |
| `bid_round` | int | 当前竞标轮次（从 1 开始） |
| `last_reopened_at` | datetime (nullable) | 上次重开竞标的时刻 |

**状态与时间字段联动规则**：
- 进入"招标中"或每次 bid_round 增量时：清空 `seat_full_deadline` 与 `seat_full_locked_at`
- 当 `seat_taken == seat_limit` 时：写入 `seat_full_locked_at = now()`，`seat_full_deadline = now() + 72h`
- 到达 `seat_full_deadline` 仍未选标/驳回 → 系统自动触发"全部驳回"（见 §5.3）
- 到达 `expires_at` 仍未选标 → `Marketplace Task → 已过期`

### D.2 Opportunity（商机）状态机

| 状态 | 含义 | 进入条件 | 可执行操作 | 当前轮次终态 | 记录级终态 | 任务重开后可再次竞标 |
|------|------|---------|-----------|:------------:|:----------:|:--------------------:|
| 待处理 | 商机已投递，等待触发竞标分析 | 商机创建（推送/拉取/派发） | 自动/手动/批量触发工作流；Owner 强制终止 | 否 | 否 | — |
| 竞标分析中 | 竞标工作流执行中 | 三种触发方式之一 | Owner 强制终止 | 否 | 否 | — |
| 已竞标 | 方案已提交任务大厅 | 工作流决策"竞标"并提交 | Owner 强制终止（仅未选标前） | 否 | 否 | — |
| 不予竞标 | 本轮决策不参与 | 工作流决策"不竞标" / Owner 强制终止 | 任务重开后 Owner 手动发起新一轮 | 是 | 否 | ✅（手动） |
| 中标 | 雇主选择该方案 | 雇主选标 | 进入 Spec 签约 | 否 | 否 | — |
| 中标失效 | 已中标但 Spec 超时未确认 | 关联 Project 因 Spec 超时 → 已取消 | 任务重开后 Owner 手动发起新一轮 | 是 | 否 | ✅（原 Opportunity 上） |
| 未中标 | 雇主选择了其他方案 | 同任务其他 Opportunity 被选标 | — | 是 | 是 | ❌ |
| 已驳回 | 雇主对本商机执行了"全部驳回" | 雇主"全部驳回"操作 | — | 是 | 是 | ❌ |
| 已过期 | 关联 Marketplace Task 自然过期/关闭 | 任务过期/关闭批量更新 | — | 是 | 是 | ❌ |

**幂等原则**：`UNIQUE(workspace_id, marketplace_task_id)`。同一 Workspace 对同一 Marketplace Task 永远只保留一条 Opportunity；多轮竞标复用该记录，历史存放在 `bid_history[]`，当前轮次由 `bid_round` 标识。

**特殊操作**：Agent Owner 可在任何非终态且未中标的 Opportunity 上执行"强制终止"→ 状态变为"不予竞标"（终止原因："Owner 手动终止"）。

### D.3 Project 状态机

| 状态 | 含义 | 进入条件 | 可执行操作 | 是否终态 |
|------|------|---------|-----------|:--------:|
| 契约签订中 | Project 已创建，等待 Spec 生成 | 雇主选标后自动创建 | 触发 Spec 签约工作流 | 否 |
| 等待雇主确认 | Spec 已提交，等待雇主操作 | Spec 签约工作流提交 Spec | 雇主确认 / 雇主不认可 → Spec 修订 / 超时兜底 | 否 |
| 契约已签订 | Spec 锁定为 spec_snapshot | 雇主确认 Spec | 自动进入 Plan 生成 | 否 |
| Plan 生成中 | Orchestrator 分析 Spec 生成 Plan | 契约已签订后自动触发 | 生成完成 → Plan 待审批 | 否 |
| Plan 待审批 | Plan 已生成，等待 Agent Owner 审批 | Plan 生成完成 | Owner 审批通过 / 驳回（回到 Plan 生成中） | 否 |
| 执行中 | Plan 已批准，Project Task 正在运行 | Owner 审批通过 / 修订完成 / 协商取消撤回 / 异常恢复 | 提交交付 / Owner 暂停 / 雇主发起协商取消 / 升级异常 | 否 |
| 异常/已暂停 | Task 异常升级或 Owner 干预暂停 | L3+ 升级 / Owner 手动暂停 | 进入人工处理 / 直接恢复到执行中 | 否 |
| 人工处理中 | 平台或 Owner 介入处理 | 从"异常/已暂停"升级 | 恢复到执行中 / 关闭 | 否 |
| 待验收 | 交付物已提交 | Agent 调用 `submit_deliverables` | 雇主验收通过 / 请求修订 / 14 天自动验收 | 否 |
| 修订中 | 雇主请求修订，回到 Spec 范围内交付内容修正 | 雇主请求修订 | 修订完成 → 待验收 / 修订耗尽 → 修订协商中 / 转纠纷 | 否 |
| **修订协商中** | 修订次数超限，进入 2 天结构化协商窗口 | 修订耗尽（`revision_count > revision_limit`） | 雇主：追加修订(A) / 转 Spec 变更(B) / 接受当前(C) / 发起纠纷(D)；窗口超时默认执行 C | 否 |
| **预算超限暂停** | Project 计算成本达到预算上限，自动暂停 | `compute_cost_used ≥ 报价 × project_compute_budget_ratio` | Owner 增加预算 → 执行中；优化 Plan → 执行中；放弃 → 协商取消中 | 否 |
| 协商取消中 | 雇主发起协商取消 | 雇主请求（Spec 签订后、非终态期间） | Owner 3 天响应 SLA；雇主 3 天确认部分结算 SLA；Owner 超时按 Project 阶段区分（执行中→按里程碑部分结算；待验收→回到待验收） | 否 |
| 纠纷处理中 | 双方无法达成一致，平台裁定 | 修订耗尽 / 协商无果 / 恶意行为 / 里程碑无法客观确认 | 平台裁定 → 执行中 / 已取消 / 已关闭 | 否 |
| 已完成 | 验收通过（含 14 天超时自动验收） | 雇主验收通过 / §9.4 自动验收条件全满足 / 修订协商窗口超时默认 C（接受当前） | 售后申诉期 7 天（`after_sale_deadline`）内可发起纠纷申诉 | 是 |
| 已取消 | Spec 超时未确认；协商取消达成一致；协商取消 SLA 超时后按里程碑部分结算完成；纠纷裁定取消；预算超限后放弃 | 见"进入条件"列 | — | 是 |
| 已关闭 | 平台裁定关闭 / 异常无法恢复 | 纠纷裁定关闭 / 异常/已暂停直接关闭 / 预算超限后关闭 | — | 是 |

**统一口径**：Project **不使用"已过期"**。所有时效性终止（Spec 超时、协商取消超时、纠纷裁定取消）统一归到"已取消"；不可恢复的异常统一归到"已关闭"。

**权限边界**：Agent Owner **不可单方面关闭** 已进入"执行中"或之后阶段的 Project；如需终止，必须走"协商取消"或"纠纷处理"业务流程。

**v0.3 新增子状态说明**：

| 子状态 | 触发字段 | 时限字段 | 关联章节 |
|--------|---------|---------|---------|
| 修订协商中 | 进入时刻写入 `revision_negotiation_deadline = now() + 2d` | 到期无操作默认 C（接受当前） | §7.7.3 |
| 预算超限暂停 | 进入时刻写入 `budget_paused_at = now()` | 无自动到期；由 Owner 主动决策 | §7.12 |

**售后申诉期**：进入"已完成"（自动验收或默认接受）时，若 `after_sale_deadline` 未写入则自动写入 `now() + 7d`，雇主可在此期间发起纠纷申诉（`已完成 → 纠纷处理中`）。7 天后申诉窗口自动关闭。

### D.4 Project Task 状态机

| 状态 | 含义 | 进入条件 | 可执行操作 | 是否终态 |
|------|------|---------|-----------|:--------:|
| 待开始 | 依赖 Task 尚未全部完成 | Orchestrator 创建 | — | 否 |
| 可执行 | 依赖已满足，等待 Agent 领取 | 依赖 Task 全部达到"完成"或"验证通过" | Agent 领取 | 否 |
| 执行中 | Agent 正在工作 | Agent 领取 | 完成 / 失败 / Owner 暂停 | 否 |
| 已暂停 | Owner 干预暂停 | Owner 手动操作 | 恢复 → 执行中 | 否 |
| 失败 | 单次执行失败 | Agent 报错 / 超时 / Gate 未过 | Harness Loop 重试 → 执行中；耗尽 → 人工处理（L4） | 否 |
| 完成 | Agent 声明完成（非里程碑节点） | Agent 完成执行 | 触发下游依赖 | 是（非里程碑） |
| 待验证 | 里程碑节点触发 Evidence Gate 校验 | 里程碑 Task 完成 | Gate 通过 → 验证通过；Gate 失败 → 验证未通过 | 否 |
| 验证通过 | Evidence Gate 全部通过 | Gate 校验通过 | 触发下游依赖 | 是（里程碑） |
| 验证未通过 | Gate 校验失败 | Gate 校验失败 | 回到执行中，计入 Harness 尝试 | 否 |
| 人工关闭 | Harness 耗尽升级 L4 后由 Owner/平台关闭 | Harness 耗尽 + L4 介入 | — | 是 |

**Harness Loop**：`失败 → 重试（自动） → 执行中`；连续失败次数超过 `harness_max_attempts`（默认 4）后升级 L4；L4 决策可选：重新分配 Agent、Owner 手动接管、标记 Project 层"异常/已暂停"、或"人工关闭"该 Task。
